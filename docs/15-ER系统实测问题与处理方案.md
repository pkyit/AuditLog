# 15 - ER 系统实测：问题分析与处理方案

**被测对象**：`io.github.pkyit:audit-log-spring-boot-starter:1.0.0`（Maven 中央仓库制品）
**测试载体**：`examples/er-demo` —— 独立 Spring Boot ER 系统（客户 / 商品 / 订单 / 订单明细，含两级外键）

**运行方式**：`java -jar` 启动 fat jar，真实 HTTP 请求，审计记录经**独立 JDBC 连接**直接读库核对

1. `er-demo` **不继承**框架父 POM、**不加入**其 `<modules>`，依赖只能从中央仓库解析——

## 三、发现的问题

### F1【阻断 · 严重】JDBC 建表 DDL 使用 `CLOB`，PostgreSQL 不支持

**现象**：`auto-create-table=true` 时宿主应用**直接启动失败**。

```
org.springframework.jdbc.BadSqlGrammarException: StatementCallback; bad SQL grammar [CREATE TABLE ...]
  at JdbcAuditStore.createTableIfAbsent(JdbcAuditStore.java:313)
Caused by: org.postgresql.util.PSQLException: 错误: 类型 "clob" 不存在  位置：182
```

**根因**：`JdbcAuditStore.createTableIfAbsent()` 的 DDL 中三处使用了 `CLOB`
（`request_body`、`response_body`、`payload`）。`CLOB` 是 Oracle/DB2 的类型，
PostgreSQL 无此类型，须用 `TEXT`。

**影响**：`jdbc` 存储 + PostgreSQL 是本框架最典型的落库组合，却无法使用。
更严重的是失败会**向上冒泡终止整个宿主应用**——引入一个审计组件导致业务系统起不来，
代价与收益完全不成比例。

**为何既有测试没发现**：框架自带测试用 H2（`MODE=MySQL`），H2 接受 `CLOB`，
因此该缺陷只在真实 PostgreSQL 上暴露。这正是"用真实依赖做端到端验证"的价值。

**严重度**：阻断。默认 `auto-create-table=false` 时不会触发，
但使用者按文档指引想省事打开该开关就会中招。

---

### F2【严重 · 静默失效】默认配置下语义通道完全不生效

**现象**：所有审计记录 `operation` / `actionType` / `resourceType` / `resourceId` /
自定义 `tags` / `transactional` **全部缺失**，`capturePlan` 恒为 `boundary`。
边界通道正常，因此**表面上看系统在采集，实际业务语义一个字段都没记**。

**根因（经 A/B 实验确证）**：

`AuditRequestContextHolder` 通过 Spring 的 `RequestContextHolder` 存取上下文：

```java
public static void set(AuditRecordContext context) {
    RequestAttributes attributes = RequestContextHolder.getRequestAttributes();
    if (attributes != null) {            // ← 为 null 时静默跳过，无任何告警
        attributes.setAttribute(ATTRIBUTE, context, SCOPE_REQUEST);
    }
}
```

`RequestContextHolder` 由 Spring 的 `RequestContextFilter` 填充，
而审计边界过滤器的**默认 order 是 -150**，早于前者，因此过滤器执行时
`RequestContextHolder` 仍为空 → `set()` **静默丢弃上下文**。
等到 Handler 执行时 `RequestContextHolder` 已有值，但属性从未写入 → `get()` 返回 null
→ `AuditLogHandlerMethod.doInvoke` 走"非过滤器路径"分支直接早退。

**实验证据**（对框架临时加诊断输出，两种 order 各跑一次）：

| 边界过滤器 order | 过滤器内 `set()` 时 | Handler 内 `get()` | 结果 |
|---|---|---|---|
| **-150（默认）** | `attrsNull=true` | `valueNull=true` → `contextNull=true` | 语义通道失效 |
| **-100** | `attrsNull=false` | `valueNull=false` | 语义通道正常 |

**为何既有测试没发现**：框架自带的 `audit-log-samples` 在
`application.yaml` 中把 `collector.boundary.order` **显式覆盖为 -100**，
恰好晚于 `RequestContextFilter`，于是绕过了缺陷。
**默认值从未被真实端到端验证过** —— 这是本次实测最有价值的发现。

**影响**：任何使用默认配置（即绝大多数使用者）的应用，
审计记录都缺失全部业务语义字段。而失败是**完全静默**的：
没有异常、没有告警日志，`/actuator/auditLog` 甚至显示
`methodEnabled=true`、`collectedMethods=6`，看起来一切正常。
这与框架自身反复强调的"绝不静默失效"原则直接冲突。

**严重度**：严重。功能名存实亡，且极易被误认为"已在工作"。

---

### F3【中】未提供建表脚本，`auto-create-table=false` 时使用者无从建表

`auto-create-table` 默认 `false`，其文档写明"建表需要 DDL 权限，
生产应由迁移脚本管理表结构"。但仓库内**没有任何 `.sql` 文件**
（已全仓检索确认）。使用者要么打开这个开关（撞上 F1），
要么自己从 `JdbcAuditStore` 源码反推 38 个字段的表结构——
而反推时同样会照抄 `CLOB`，在 PostgreSQL 上继续失败。

**影响**：把"生产应自行管理表结构"这一正确建议变成了不可执行的建议。

---

### F4【中】依赖编译期 `-parameters`，缺失时表现为莫名 400

**现象**：使用者若未开启 `-parameters`，`@PathVariable Long id` 这类写法
在运行期返回 400，错误信息为：

```
Name for argument of type [java.lang.Long] not specified, and parameter name
information not available via reflection. Ensure that the compiler uses the '-parameters' flag.
```

**根因**：Spring MVC 与审计框架都依赖方法参数名（框架用于 `resourceIdParam`
与实参表达式解析）。框架自身的父 POM 设置了 `<parameters>true</parameters>`，
但**外部使用者不会知道这个要求**，且缺失时是运行期错误而非编译期错误。

**影响**：对使用者是纯额外的排查成本；对框架是"未声明的前置条件"。

## 四、其他观察（非缺陷，但值得记录）

### O1 `ActionType` 无语义粒度区分增/改/删

枚举取值为 `UNKNOWN/AUTHENTICATE/AUTHORIZE/QUERY/MUTATE/EXPORT/IMPORT/CONFIGURE/ADMIN`，
增删改统一为 `MUTATE`。这是明确的设计取舍（枚举注释已写明"数据变更：新增、修改、删除"），
审计区分靠 `@AuditLog(name=...)`。对需要按"增/改/删"做统计的下游，
只能解析 `operation` 文本。**本次不改**，仅记录取舍，建议在文档中给出下游分类指引。

### O2 测试断言写错（本文档作者的问题，非框架缺陷）

断言"仅首条记录 `prev_hash` 为空"失败，原因是链状态持久化在
`chain.state-file` 中，与审计记录表**相互独立**：清空记录表不会重置链头，
因此新一轮的首条记录 `prev_hash` 指向上一轮的链头。
这**正是防篡改设计应有的行为**（否则删表即可洗白历史），是断言写错了。已纠正认知。

### O3 PostgreSQL 下 `GeneratedKeyHolder.getKey()` 需显式指定列名

示例工程初期用 `Statement.RETURN_GENERATED_KEYS` 取主键，
PostgreSQL 驱动会回传**整行**，导致：
`The getKey method should only be used when a single key is returned`。
改用 `prepareStatement(sql, new String[]{"id"})` 后正常。
这是使用者接入 PostgreSQL 时的常见坑，建议写入框架文档的示例。

### O4 缓存代理对新发布坐标存在同步延迟

发布后实测 aliyun 公共仓库出现"POM 已同步、JAR 仍 404"的中间状态。
排查"制品能否被外部解析"这类问题时必须直连 `repo1.maven.org`，
否则会把代理问题误判为发布问题。（已在 `tools/settings-central-direct.xml` 固化该做法。）

## 五、处理方案

### 5.1 F1：DDL 类型按数据库方言选择

* **方案**：不硬编码 `CLOB`。由 `DataSource` 的 `DatabaseMetaData.getDatabaseProductName()`
  推导大文本列类型：Oracle / DB2 用 `CLOB`，其余（PostgreSQL、MySQL、MariaDB、H2、SQLite、
  SQL Server）用 `TEXT`；推导失败时回退 `TEXT`。
* **理由**：`TEXT` 覆盖绝大多数目标库；Oracle 系必须 `CLOB` 才是原设计意图，
  保留兼容而不是简单替换成 `TEXT` 而破坏 Oracle 使用者。
* **配套**：把推导结果打日志（"审计表使用大文本类型=TEXT（数据库=PostgreSQL）"），
  让方言选择可见、可排查。
* **验收**：在 PostgreSQL 上 `auto-create-table=true` 能建表并启动成功；
  H2 用例继续通过；对 Oracle 仅做单元级断言（无实例，不谎称已实测）。

### 5.2 F2：上下文承载改为"请求属性 + 兜底"，且失败必须可见

* **方案**：`AuditRequestContextHolder` 改为
  1. 优先把上下文写入 **Servlet 请求属性**（过滤器阶段就可用，不依赖 `RequestContextHolder`）；
  2. 读取时先试当前请求属性，再回退到 `RequestContextHolder`，最后回退到 `ThreadLocal`；
  3. **任何一次 `set()` 无法落地都必须 WARN**，绝不静默。
* **理由**：`RequestContextHolder` 的填充时机取决于过滤器顺序这一**外部因素**，
  框架把自身正确性建立在它之上本身就是脆弱设计。
  请求属性在过滤器阶段必然可用，是唯一不依赖顺序的载体。
* **附带修复**：过滤器启动日志显式打印 `RequestContextFilter` 的顺序关系提示；
  并在启动校验中检测"审计过滤器 order 是否早于 `RequestContextFilter`"，
  若早于则在 1.0.1 起改为无需检测（因已不依赖它）。
* **验收**：`er-demo` 用**默认 order**（-150）跑，`operation`/`actionType`/
  `resourceType`/`resourceId`/`tags`/`transactional` 全部有值；
  并把 order=-150 与 -100 两种取值都纳入回归，防止再次只测一种配置。

### 5.3 F3：随制品提供建表脚本

* **方案**：新增 `audit-log-spring-boot-starter/src/main/resources/db/` 下按数据库方言的
  DDL（至少 PostgreSQL / MySQL / Oracle 三份），并在 README 与配置项注释中指向它。
* **理由**：让"生产自行管理表结构"成为可执行建议。

### 5.4 F4：启动期校验 `-parameters`

* **方案**：启动校验新增一项——检测 `@AuditLog` 所在方法是否保留了参数名
  （`Method.getParameters()[i].isNamePresent()`）。缺失时**明确告警**并指出
  需要开启 `-parameters`，而不是让使用者在运行期撞 400。
* **理由**：把"未声明的前置条件"变成"启动即告知"。

### 5.5 回归测试补强（针对"只测一种配置"这一根本教训）

* 框架自带端到端验收**删除对 `boundary.order` 的覆盖**，改用默认值运行，
  使默认配置纳入持续验证；
* 新增一条用例：同一应用内分别以 `order=-150` 与 `order=-100` 启动，
  断言两者语义字段均完整；
* `er-demo` 的验证脚本纳入仓库，作为跨数据库/跨容器的外部消费验证入口。

## 九、修复过程中新发现的问题

### F5【中 · 影响结果真实性】事务边界在 Service 层时，事务信息采集不到

**现象**：`er-demo` 的下单接口事务边界在 `OrderService.create()`（`@Transactional`），
审计记录中 `transactional` 始终为 `false`，`rolledBack` 也永远不会置位。

**根因**：`TransactionAuditTracker.register(context)` 由 `AuditLogHandlerMethod.doInvoke`
在**控制器方法**入口调用，而该方法第一件事就是判断
`TransactionSynchronizationManager.isSynchronizationActive()` —— 分层架构下事务由
Service 层开启，控制器入口处同步尚未激活，于是直接返回、不注册回调。

**为何既有测试没发现**：框架自带示例的事务边界在控制器层（或处理器内部），
调用 register 时同步已激活，因此通过。**真实分层架构普遍把事务放在 Service 层**，
两者行为不同。

**影响**：这不是"少一个字段"那么简单。
`drop-on-rollback` 依赖 `ROLLED_BACK` 判定来决定是否留档 —— 判不出来，
就意味着"事务回滚了但异常被上层吞掉、接口仍返回成功"的场景下，
审计会记录一次**并未真正发生**的操作，直接冲击"结果可信"这一不变量。

本次 `er-demo` 中库存不足会抛异常并传播，因此 `outcome` 仍被如实记为 `FAILURE`
（走的是异常路径而非事务路径），未被误报为成功；但依赖事务路径的场景存在风险。

**处理方案（建议 1.0.2）**：改为在**事务真正开始时**注册回调，而不是在控制器入口。
可行做法是提供一个基于 `AnnotationMatchingPointcut` 的 Advisor，
拦截 `@Transactional` 方法并注册审计同步；未引入 spring-aop 时降级为当前行为
并明确告警。该改动涉及 AOP 织入顺序，需要独立的验证设计，故不在 1.0.1 中一并实施。

**当前状态**：`er-demo` 的验证脚本将其列为"已知局限"单独输出，
不计入回归失败，避免它掩盖真实回归。



```bash
# 1. 建库（本机无 psql，使用仓库自带的 SqlRunner）
java -cp "<classes>;<postgresql.jar>" SqlRunner \
     jdbc:postgresql://10.10.10.101:5432/postgres postgres <pwd> -e "CREATE DATABASE er_demo"

# 2. 构建示例（空本地仓库 + 直连中央仓库，确保用的是已发布制品）
cd examples/er-demo
mvn -B -s ../../tools/settings-central-direct.xml \
    -Dmaven.repo.local=<empty-repo> -DskipTests package

# 3. 全量验证（业务 + 审计，审计结论直接读库）
python verify-er.py
```
