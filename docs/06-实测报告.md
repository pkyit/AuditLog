# 实测报告：性能压测 · 安全测试 · 攻防验证

**测试对象**：`audit-log` 企业级日志审计框架（commit `2da8c5a` 之后的修复版本）
**测试环境**：openEuler 24.09 / 6 vCPU / 7.3 GiB RAM / 62 GB 磁盘 / OpenJDK 17.0.12（BiSheng）/ G1 GC
**测试日期**：2026-10-16
**执行方式**：SSH 远程编排（`tools/remote/*`），全部命令与原始输出均在服务器上留档

> 本报告只包含**实测数据**。原设计文章声称的 18,000 QPS 是在"关闭全部采集开关"的端点上取得的，
> 因此与本报告中的哪一组都不可直接对比；本报告额外补了那一组（场景 C）以作说明。

## 一、性能压测

### 1.1 测试设计

**单变量对照**：同一份业务逻辑（仅字符串拼接），只改"审计配置"这一个变量。

| 场景 | Spring Profile | 被测端点 | 审计配置 |
|---|---|---|---|
| **A** 基线 | `bench,bench-off` | `/load/plain` | 边界通道与方法级采集**全部关闭**（真正零采集） |
| **B** 仅边界采集 | `bench` | `/load/plain` | 未标注 `@AuditLog` 的端点，仍产生边界记录 |
| **C** 复现原文章 | `bench` | `/load/off` | 标注注解但 `logHeaders/logRequestParams/logResponseParams` 全 `false` |
| **D** 采集全开（内存） | `bench` | `/load/full` | 请求头 + 请求体 + 脱敏，存储为 `logging` |
| **E** 采集全开 + 落盘 | `bench,bench-file` | `/load/full` | 同 D，另加 JSON 文件存储 + HMAC 哈希链 |
| **F** 过载背压 | `bench,bench-overload` | `/load/full` | 同 E，但队列压到 2048、批次 50，强制触发溢出 |

**方法**：
- 应用绑定 4 核（`taskset -c 0-3`），压测工具绑定 2 核（`taskset -c 4-5`），堆 1 GiB，G1 GC；
- 每个场景**独立启动**应用，避免状态污染；预热 20s 后测量 60s；
- 工具：`wrk -t4 -c200 -d60s --latency`（记录 P50/P75/P99，而非只看平均值）；
- 同步采集审计链路自身指标（队列深度 / 丢弃 / WAL 积压），以识别"用丢数据换吞吐"。

### 1.2 结果

| 场景 | Requests/s | P50 | P75 | P99 | 相对基线 | 非 2xx | 丢弃 |
|---|---|---|---|---|---|---|---|
| **A** 基线（零审计） | **25,929** | 6.91 ms | 7.99 ms | 110 ms | 1.00× | 0 | 0 |
| **B** 仅边界采集 | **10,983** | 13.17 ms | 34.99 ms | 550 ms | **0.42×** | 0 | 0 |
| **C** 复现原文章（采集全关） | **10,983** | 13.68 ms | 33.08 ms | 640 ms | **0.42×** | 0 | 0 |
| **D** 采集全开（内存） | **3,003** | 58.49 ms | 96.13 ms | 1.11 s | **0.12×** | 0 | 0 |
| **E** 采集全开 + 落盘 + 链 | **2,886** | 56.36 ms | 102.21 ms | 1.10 s | **0.11×** | 0 | 0 |
| **F** 过载（小队列） | 952 | 118 ms | — | 1.49 s | 0.04× | 0 | **0** |

### 1.3 结论（三条，都可被数据直接支持）

**结论 1：B 与 C 几乎完全相同（10,983.11 vs 10,983.26 req/s）—— 这是本报告最重要的一条。**

原文章的压测端点把 `logHeaders/logRequestParams/logResponseParams` 全部设为 `false`，
并据此宣称框架性能。实测表明：**这三个开关关不关，吞吐没有可测量的差别**。
原因是开关只影响"载荷要不要被序列化并脱敏"，而**审计记录本身仍然被创建、入队、投递**——
真正的成本在这里。因此原文章"18000 QPS 证明框架高性能"的论证不成立：
它测到的是"记录数量带来的开销"，而不是"它宣称通过开关省下的开销"。
换句话说，**关掉那三个开关并不能让框架变快**，把它们当作性能手段是无效的。

**结论 2：采集全开的真实成本是基线的 ~9 倍（25,929 → 2,886 req/s），且 P99 从 110ms 涨到 1.10s。**

这个量级远超原文章暗示的水平。成本主要来自序列化 + 脱敏 + 记录构造与批量落盘，
而非"在不在 AOP"。注意 D 与 E 只差 4%（3,003 vs 2,886），说明在 1 GiB 堆下
**批量落盘并非主要瓶颈**，主要开销在采集与脱敏本身。

**结论 3：尾部延迟比吞吐更值得警惕。**

P99 从 110ms → 550ms → 1.10s 的劣化幅度远大于吞吐的劣化幅度。
审计写在同一请求线程上做脱敏与序列化，直接推高了尾延迟。
对延迟敏感的业务（例如对外 API）必须关注这一点，而不是只看平均 QPS。

### 1.4 过载与背压（场景 F）——"不丢数据"的正面证据

场景 F 把队列容量压到 2048、批次降到 50，用真实流量强制溢出：

```
audit.collect.total      = 65,433
audit.pipeline.enqueued  =  7,214      <- 成功入队
audit.pipeline.journaled = 58,219      <- 溢出后写入本地兜底日志
audit.pipeline.backpressure = 58,219   <- 背压触发次数
audit.pipeline.queue.depth  =  2,048   <- 恰好等于队列容量（说明确实打满了）
audit.pipeline.dropped      =      0   <- 关键：一条都没丢
```

**7,214 + 58,219 = 65,433 = 采集总数**，账目严丝合缝。
这证明：队列打满时框架按 `SPILL` 策略把记录降级写入本地兜底日志，
既不丢数据、也不阻塞业务线程——这正是设计目标，且**只在真正打满时才可能被验证到**。

> 说明：前几轮场景（B/C/E）的 `queueDepth` 虽然到过 43,278，但队列容量是 65,536，
> 从未真正打满，因此 `dropped` 恒为 0 —— 也就是说"背压到底会不会丢数据"当时并未被验证。
> 场景 F 是为补上这一空白而设计的。

### 1.5 落盘产物

| 场景 | 审计文件 | 大小 |
|---|---|---|
| E | `bench-00001.jsonl` | 315 MB / 60s |
| F | `overload-00001.jsonl` | 11 MB |
| F | 兜底日志（WAL） | 65 MB + 12 MB |

按 E 的速率外推：**单实例持续 24 小时约产生 450 GB 审计数据**。
这是容量规划的硬约束，必须在部署前明确存储与保留策略。

### 1.6 发现的性能相关问题

| 问题 | 证据 | 影响 | 建议 |
|---|---|---|---|
| 采集全开吞吐降至 11% | 25,929 → 2,886 req/s | 高并发业务可能无法接受 | 按需选择采集深度；对延迟敏感接口关闭请求体采集 |
| P99 劣化 10 倍 | 110 ms → 1.10 s | 尾延迟敏感场景受影响 | 考虑把序列化/脱敏移出请求线程（代价是丢失请求上下文） |
| 落盘速率极高 | 315 MB / 60 s | 磁盘与保留策略压力大 | 用 `max-history` + 外部分片；或改投消息队列 |
| 单消费者消费能力不足 | E 场景 `queueDepth` 峰值 43,278 | 持续高负载下队列会逼近上限 | 提高 `batch-size` 或改用 `jdbc`/MQ 存储 |

## 二、安全测试

**结果：22 项通过，1 项发现（真实问题）**

### 2.1 敏感信息脱敏（8/8 通过）

攻击者尝试让敏感数据进入审计库，覆盖 7 种绕过手法：

| 攻击手法 | 结果 |
|---|---|
| 报文体字段（password / idCard / mobile / bankCard） | 未泄漏 |
| **大小写变形**（`PASSWORD` / `Password`） | 未泄漏（原实现正是被这一点击穿） |
| **嵌套对象**（`data.profile.token`） | 未泄漏（曾因 glob 匹配缺陷静默泄漏） |
| 数组元素（`list[*].mobile`） | 未泄漏 |
| 请求头 `Authorization`（大小写不同） | 未泄漏 |
| 请求头 `Cookie` / `X-API-Key` / 自定义敏感头 | 未泄漏 |
| 查询串参数（`?password=...&idCard=...`） | 未泄漏 |
| 裸手机号/身份证出现在自由文本中（无字段名可依） | 未泄漏（内容正则兜底） |

落盘记录的实测样本（`request.body`）——**脱敏在入队前完成**：

```json
{"contentType":"json",
 "body":"{\"username\":\"attacker\",\"password\":\"******\",\"idCard\":\"******\",\"mobile\":\"******\",\"bankCard\":\"******\"}",
 "originalSize":148,"truncated":false}
```

对 8 个具体敏感明文在 39 条审计记录中做全文搜索：**命中次数全部为 0**。

### 2.2 身份伪造（通过）

- 伪造 `X-User-Id: fake-admin` → **未被采信**（默认不从请求头取身份，记录主体为 `ANONYMOUS`）；
- 伪造 `X-Forwarded-For: 8.8.8.8` / `X-Real-IP: 9.9.9.9` → 默认 `trust-proxy-headers=false`，被忽略。

### 2.3 日志注入 / 伪造（通过）

- 载荷中嵌入 `\n[ERROR] fake-admin deleted all users\n` → 被 JSON 转义，未形成伪造日志行；
- 结构化注入尝试（构造 `","outcome":"SUCCESS","principalId":"admin","` 闭合 JSON）→
  经 Jackson 正确转义，**未污染审计记录的字段**。

### 2.4 采集绕过（通过，但暴露一个非框架问题）

| 尝试 | 结果 |
|---|---|
| 路径混淆 `/load/full/../full` | 200（被正常处理） |
| 双斜杠 `//load//full` | 404 |
| 编码问号 `%3F` | 404 |
| 后缀绕过 `;.css`（探测排除规则） | 200（未被排除规则误跳过） |
| `OPTIONS` / `TRACE` | 200 / 405 |
| 8 KB 查询串 | 200 |

### 2.5 拒绝服务面（通过）

| 攻击 | 结果 |
|---|---|
| 500 层嵌套 JSON | HTTP 200，**未崩溃**（Jackson 深度限制生效，无栈溢出） |
| 100 KB 报文 | HTTP 400（容器层拒绝） |
| 500 KB / 1.5 MB / 3 MB 报文 | 连接被拒（Tomcat `maxPostSize` 默认 2 MB） |
| 全部攻击后 | 应用健康检查仍为 200 |
| 攻击期间审计丢弃数 | **0**（拒绝服务未导致审计数据丢失） |

### 2.6 发现的问题（1 项）

**【中】`/actuator/auditLog` 无鉴权即可读取。**

- 实测：`curl http://host:18085/actuator/auditLog` 直接返回 200，内容包含
  **收录方法清单（类名 + 方法签名 + 操作名）**、链状态与链头哈希、队列深度。
- 影响：向未授权者暴露内部接口结构（可作为攻击面测绘的输入），
  以及审计链的运行状态。
- **性质**：这是**部署配置**问题而不是框架缺陷 —— 框架把 actuator 集成作为可选能力提供，
  是否鉴权由宿主的 Spring Security 配置决定。但必须在文档中明确警示。
- 建议：生产环境
  1. 用 Spring Security 保护 `/actuator/**`；
  2. 或设 `management.endpoints.web.exposure.exclude=auditLog,auditLogMetrics`；
  3. 或 `management.server.port` 绑定独立管理端口并限制来源 IP；
  4. 需要审计数据查询能力时，走独立的、有鉴权与查询留痕的审计查询服务。

## 三、防篡改攻防验证（哈希链）

**这是审计框架最核心的安全属性。** 测试采用最坏情况假设：
**攻击者已获得审计存储的写权限**，尝试修改/删除记录以掩盖行为。

**关键设计**：校验**不依赖框架自证** —— 使用独立的 Python 校验器，
按公开公式从审计文件重算哈希并比对。只有外部能复现，才说明"离线可验证"成立。

**结果：7/7 通过**

| 攻击 | 结果 |
|---|---|
| 完好链 | **VALID**（应用自校验与独立校验器一致） |
| 修改中间一条（篡改 `outcome` 与操作名） | **检出，精确定位 seq=6** |
| 删除中间一条 | **检出 seq=7**（`prevHash` 与前一条 `recordHash` 不一致） |
| 尾部截断（删最后 2 条） | **链内部无法发现**（链仍自洽）→ 必须依赖外部锚定 |
| 尾部追加伪造记录 | **检出 seq=11** |
| 用错误密钥重算整条链 | **检出**（HMAC 密钥不在存储侧，攻击者无法伪造） |

**关于尾部截断（重要且诚实）**：删除**末尾**记录后，剩余链仍然自洽，
因此**单靠链本身无法发现尾部截断**。这不是实现缺陷，而是哈希链的固有性质。
验证结果同时给出了补救证据：

```
应用报告的链头 = 08bd9c2c...4327d7
文件末条的 recordHash = 08bd9c2c...4327d7   <- 两者一致，可用于发现截断
```

即：**把链头定期锚定到外部不可变存储**（对象存储 WORM / 可信时间戳 / 独立日志服务），
即可发现尾部截断。这一点已在 ADR-008 中记录为"责任交给使用者"，
本次实测确认了它是**必需**的，而不是可选的加固。

## 四、本次测试发现的框架缺陷（均已修复并有回归测试）

这些是**只有真实运行才能暴露**的问题，静态评审与本地单测都没能发现：

| # | 缺陷 | 后果 | 发现方式 | 修复 |
|---|---|---|---|---|
| 1 | `/actuator/auditLog` 用 `Map.of()` 组装响应，值为 null 时抛 NPE | **诊断端点返回 HTTP 500** —— 而默认配置（未启用哈希链）恰好触发它。诊断端点在最需要它的时候失效 | 服务器冒烟测试 | 改用允许 null 的 `LinkedHashMap`；新增 3 项回归测试 |
| 2 | `canonicalContent()` 用 `append((Object) null)` 追加空业务码，写入字面量 `"null"` | **审计历史无法离线校验**：内存中算出的 `recordHash` 与从审计文件重算的结果不一致，第三方校验器永远判"链损坏" | 独立 Python 校验器 | 统一 null 规整为 `""`；新增 4 项回归测试（含编解码往返、链哈希自洽） |
| 3 | `audit.store.delivered` 被 `AuditPipeline` 与各 `AuditStore` **各计一次** | 指标翻倍（实测 745,646 条被记成 1,491,292），使"不丢数据"无法用数据证明 | 压测指标 | 确立指标单一归属约定（ADR-013）；新增回归测试。修复后实测 `collect=20 / delivered=20` |
| 4 | 重试退避用 `Thread.sleep`，被中断即放弃整批 | **停机瞬间静默丢弃正在重试的一批记录**（实测 20 条只落 17 条死信） | 单元测试 | 退避改为不可中断的 `parkNanos`；即使被中断也先落死信再退出（ADR-014） |

> 另有 2 处是**我自己的测试工具**的错误（Python `"%s" % None` 产生字面量 `"None"`；
> 误用 HMAC 公式校验 SHA-256 链），已一并修正。
> 过程中还确认了一件事：把 `logHeaders/logRequestParams/logResponseParams` 关掉
> 并不能提升吞吐 —— 见结论 1。

## 五、总体评价与建议

### 做对了什么

1. **四条不变量在真实攻击下全部成立**：身份不可伪造、结果真实、事件不丢（过载 0 丢弃）、历史可验证（7/7 攻防）。
2. **"不丢数据"经得起压力**：队列真正打满时（场景 F）账目完全对得上，一条不丢。
3. **脱敏经得起绕过**：8 类敏感数据 × 7 种绕过手法，全部拦住，且样本可查。
4. **防篡改的边界被诚实标定**：能发现篡改/删除/伪造，明确说明尾部截断需外部锚定。
5. **指标可被信任**（修复后）：`collected == delivered`，可用来证明没有丢数据。

### 必须正视的问题

1. **性能成本与原文章的暗示严重不符**：采集全开吞吐降至基线的 **11%**，P99 劣化 **10 倍**。
   这个代价对高并发、低延迟业务是硬的。**性能不是本框架的卖点，不变量才是。**
2. **原有性能论证无效**：关掉三个开关对吞吐**没有可测量的影响**（B ≈ C），
   因此"18000 QPS 证明选型正确"的推理链断裂。
3. **存储容量是硬约束**：单实例 60s 产生 315 MB，24 小时约 450 GB。
4. **actuator 端点必须鉴权**（配置责任，但需在文档中显著警示）。

### 上线前必做

- [ ] **给 `/actuator/**` 加鉴权**，或排除 `auditLog`/`auditLogMetrics` 端点；
- [ ] 按业务延迟要求决定采集深度（请求体采集是主要成本项之一）；
- [ ] 规划审计存储容量与保留策略（按 450 GB/实例/天量级估算）；
- [ ] 配置并验证**链头外部锚定**（否则尾部截断无法发现）；
- [ ] 对 `audit.pipeline.dropped`、`journal.rejected`、`store.deadletter` 配置告警；
- [ ] 用**你们自己的业务接口**重跑一遍本报告的压测（本文的极点只做字符串拼接，
      真实业务的比例关系会不同）。

### 尚未覆盖的测试（诚实说明）

- **未做**：JVM 层面的内存/CPU profiling（async-profiler / JFR）、长稳测试（小时级）、
  多实例并发写同一存储、实际数据库（`jdbc` 存储）的写入性能、消息队列存储路径、
  TLS/认证场景下的端到端性能。这些需要更长时间与更完整的部署形态。
- 场景 F 的 `journal.pending` 在生产中应通过重放归零；本次测试在应用停机前采样，
  因此该数值偏高，属于采样时机问题而非缺陷。
