# 整改方案自评审（Adversarial Review of `02-整改方案.md`）

评审人立场：假设我是接收这个方案的平台架构师，职责是**找出它在落地时会怎么坏**。
评审对象是 `docs/02-整改方案.md` 自身，不是原代码。

结论：方案方向成立，但有 **9 处设计缺陷** 必须在实施前修正，其中 3 处（D1/D2/D3）会直接导致「改了但没解决原问题」。

---

## D1（严重）双通道用 `requestId` 事后合并 → 引入竞态，可能把审计弄丢

**方案原文**：边界通道与语义通道「用 `requestId` 关联，语义通道存在时补齐并覆盖边界通道的粗粒度记录」。

**为什么坏**：
- 语义通道记录经过**有界队列 + 异步消费者**到达存储，边界通道记录在 `afterCompletion` 才产生。两者到达存储的顺序**不确定**：「覆盖」可能变成「被覆盖」，最终留下粗粒度那条，**操作名、资源 ID、变更快照全丢** —— 恰好丢掉审计最需要的语义。
- 若在内存里按 `requestId` 做关联表，就重新引入了「跨请求共享可变状态 + 泄漏风险 + 锁竞争」，正是要消除的原设计问题。

**修正（采纳）**：**不做两条记录、不做事后合并**，改为**一条记录、两个阶段填充**：
- `OncePerRequestFilter` 在建请求上下文时创建**一个** `AuditRecordBuilder`，放进 `AuditContext`（挂在 request attribute 上）；
- 语义通道（HandlerAdapter）**只往这个 builder 里填**操作名/动作类型/资源/变更快照/耗时，**不发布**；
- 边界通道在 `afterCompletion` 填真实状态码/最终异常/响应耗时，然后**唯一一次发布**，并把 builder 冻结为不可变 `AuditRecord`。
- 无合并、无竞态、无关联表、无共享可变状态；`requestId` 仅用于与其他系统日志关联。

**副作用（须记录）**：语义通道不再独立发布 → 若宿主用了自己的 `WebMvcRegistrations` 且未开启方法通道，功能退化为纯边界采集（这是**可接受的降级**，且不再有重复记录问题）。

## D2（严重）`commitMode=REQUIRED_SAME_TX` 与异步流水线自相矛盾

**方案原文**：提供 `REQUIRED_SAME_TX`「记录写入由用户 `AuditStore` 在同一事务内落库」。

**为什么坏**：异步流水线的存在前提是「采集与业务解耦」。若要求同事务写入，则：
- 必须**同步**调用 `AuditStore.save`（在业务事务内），否则事务上下文不存在；
- 一旦同步写库，背压、队列、WAL、批量全部失效，且业务事务被审计库的可用性绑架（审计库挂了业务全挂）；
- 这与「不丢」目标其实冲突：同事务写入把「审计可用性」变成「业务可用性」的单点。

**修正（采纳）**：
- **删除** `REQUIRED_SAME_TX` 枚举，避免给出一个自相矛盾且危险的承诺；
- 改为提供 `commitMode` 两值：`EVENTUAL`（默认，立即投递）与 `AFTER_COMMIT`（提交后投递）；
- 若用户确实需要强一致，正确的做法是**让用户的 `AuditStore` 自己决定**：`AuditStore` 接口增加 `boolean supportsSameTransaction()`，框架在 `AFTER_COMMIT` 模式下若存储声明支持，则交给存储实现（框架不承诺）；并在文档中明确「强一致是以业务可用性换取审计可用性，需自行评估」。

## D3（严重）「回滚记录为 `ROLLBACK`」仍是一次假阳性

**方案原文**：`AFTER_COMMIT` 模式下「提交后投递、回滚则改写为 `ROLLBACK` 并投递」。

**为什么坏**：回滚意味着**什么都没发生**。为一次未生效的操作留一条记录，恰恰是原评审 F2 指责的「记录了没发生的事」的另一种形式；等保场景下会污染审计结论（例如「管理员删除了用户 X」但实际回滚了）。

**修正（采纳）**：把选择权显式化，默认取「不产生假阳性」：
- 新增 `audit.log.commit-mode.after-rollback`: `DROP`（**默认**）| `RECORD`
- `DROP`：回滚不产生审计记录（记录「无事实」，符合审计语义）；
- `RECORD`：写入一条 `Outcome=ROLLBACK` 且 `result=FAILURE`、`detail` 明确标注「事务已回滚，操作未生效」的记录，供「尝试性操作」审计；
- 无论哪种模式，**都不得**把回滚记成成功（这是原缺陷的实质）。

## D4（高）默认「记录请求体 + 一律序列化方法实参」仍是原 H4 的隐患

**方案原文**：`collector.method` 默认开启，且请求体默认记录。

**为什么坏**：序列化**任意** Java 实参是原实现最危险的举动（懒加载、循环引用、超大对象、框架参数噪音）。默认可写，就等于默认把这个问题带给使用者。

**修正（采纳）**：分层默认，安全优先：
- **方法实参默认不序列化**（`collector.method.serialize-arguments=false`）；改为**从缓存的请求体/查询串生成结构化快照**（来源稳定、可控大小、可结构化脱敏）；
- 需要记录实参时显式开启，并且：
  - 跳过框架类型（`ServletRequest/Response`、`Principal`、`Model`、`BindingResult`、`MultipartFile`、`InputStream`、`Writer`、`Locale`、`TimeZone`…）与 `@AuditIgnore` 标注的参数；
  - 每次序列化包在独立 try-catch 内，单项失败**只记占位符**，不影响其他字段与业务；
  - 强制长度上限（默认 4KB）+ 深度上限 + 循环引用检测（Jackson 已含）；
- 响应体默认 **false**（保持方案原判），且仅做「结构化摘要 + 大小」而非全文。

## D5（高）WAL 降级发生在**请求线程**内 → 背压把 SLA 风险从内存转移到磁盘

**方案原文**：队列满 → `SPILL` 写本地 WAL。

**为什么坏**：SPILL 是在 `offer` 失败后、于**业务请求线程**上执行磁盘 I/O。磁盘慢（或磁盘满）时，这个「保护业务」的策略反而变成新的业务阻塞源，且与「不阻塞 SLA」的初衷冲突。

**修正（采纳）**：
- WAL 写入采用**异步单写线程 + 独立有界文件缓冲**，请求线程只做「入 WAL 队列」，且该入队**不阻塞**；
- WAL 自身队列也满时，最后一次降级是**内存缓冲 + 计数**，并把 `journalRejected` 计入指标 + 触发 `AuditFailureHandler`（**明确暴露**，不假装没丢）；
- 文档写清三级降级：`队列满 → WAL 队列 → WAL 内存缓冲 → 丢弃+告警`，每级都有指标。

## D6（中）`AuditChain` 在多消费者并发投递下无法保证 `prevHash` 唯一

**方案原文**：「由 `AuditHashChain` 在投递前按批次串行计算」。

**为什么坏**：若消费者线程数 > 1，则批次之间并发计算 → 两个批次引用同一个 `prevHash` → 链分叉，校验失败。

**修正（采纳）**：把**发号与链接纳入单点**：
- 默认消费者为**单线程投递**（`consumerThreads=1`）以保证链严格串行；
- `consumerThreads>1` 时，账号分配在**入队时**用原子步进完成（`seq` 在 `offer` 前分配），链式哈希在**存储前由单线程聚合器**按 `seq` 排序串行计算；
- 若用户关闭链（`chain.enabled=false`），允许完全并发投递；
- 文档给出「链 + 并发」的明确约束矩阵（这是必须写清的架构约束，而不是留给使用者猜）。

---

## D7（中）「启动期交叉校验」默认只告警 → 与原 H1「静默失效」的诉求打了折扣

**方案原文**：`validation.failOnMismatch` 默认告警。

**修正（采纳）**：分两级，既不大面积搞崩宿主，也不允许静默：
- **启动期强校验**（默认 `fail-fast`）：`@AuditLog` 注解被配置**排除**、或注解所在方法**不是** Handler 方法（写错了位置）→ 启动失败（这是使用者的明确错误，必须立刻暴露）；
- **运行期弱校验**（默认告警 + 指标）：HandlerMapping 中的方法与配置集合的差异 → 每次请求未命中都计入 `unmatched` 指标，并在首次出现时打印一次 WARN（含方法签名）；
- 提供 `/actuator/auditLog` 端点输出收录清单，便于人工核对。

---

## D8（中）保留期 / 文件轮转在原方案里只是一句「策略」，没有落点

**修正（采纳）**：默认实现必须自带生命周期，否则「只增不减打满磁盘」这条原缺陷没被真正修掉：
- `JsonFileAuditStore` 支持 `max-file-size`、`max-history`、`rotate-on-startup`；
- 提供 `RetentionPolicy` SPI，默认 `SizeAndCountRetention`；
- 启动与轮转时执行清理，清理动作本身**计入审计（审计的审计）**：记录到同一 journal 的 `retention` 事件。

---

## D9（中）离线环境无法运行 JUnit（surefire provider 缺失）→ 验收方式必须换

**事实**：本地仓库 `E:/.m2/repository` 中不存在 `surefire-junit-platform`（且无外网），`mvn test` 无法执行 JUnit 5 测试。

**修正（采纳）**：不把验收押在 surefire 上：
- 在 `audit-log-core` 内提供**零依赖断言运行器**（`AuditSelfCheck`），可在 `main` 直接跑；
- 在 `samples` 提供**端到端验收应用**：以 `java -jar` 启动，访问真实端点，再由独立的 `AuditAcceptanceRunner`（进程内）断言审计产物；
- 同时保留标准 JUnit 测试源码（结构完整、可在有网环境直接 `mvn test`），实现「离线可验、联网可跑测试」双轨；
- 明确在 README 记录该环境约束与两种验证方式。

## 其他次要修正

- **D10** `AuditRecord` 不可变，采集期用 `AuditRecordBuilder`（避免半构造对象泄漏）。
- **D11** 默认 `store=logging` 必须显式 WARN「未配置持久化存储，审计数据不符合合规留存要求」，避免默认配置给人「已合规」的错觉。
- **D12** 健康检查需区分「未配置持久存储（UP 但带告警）」与「队列积压/存储不可用（DOWN）」。
- **D13** IP 解析：默认不信任代理头；若开启，必须提供**可信代理网段**配置，否则等于把 IP 交给客户端伪造。
- **D14** 性能验收（A11）必须包含**采集全开 + JSON 落盘**这一组，否则重复原评审 F1 的错误（用关掉采集的数据证明性能）。
- **D15** `AuditLogDO` 兼容别名不应长期双轨：标注 `@Deprecated(forRemoval=true)` 并写明移除版本。

## 修正后的实施要点（差异汇总）

| 编号 | 原方案 | 修正后 |
|---|---|---|
| D1 | 双通道按 requestId 事后合并 | 单记录两阶段填充，边界通道唯一发布 |
| D2 | 三值 commitMode（含同事务） | 两值 + `supportsSameTransaction()` 交由存储 |
| D3 | 回滚一律记 `ROLLBACK` | `after-rollback: DROP`（默认）/ `RECORD` |
| D4 | 默认序列化方法实参 | 默认不序列化实参，改用请求体/查询串快照 |
| D5 | SPILL 在请求线程写 WAL | WAL 独立异步队列 + 三级降级 + 全量指标 |
| D6 | 批次串行计算链 | 入队发号 + 单线程聚合器串行成链，给约束矩阵 |
| D7 | 交叉校验只告警 | 启动强校验 fail-fast + 运行期弱校验 + 端点核对 |
| D8 | 保留策略未落地 | 内置轮转/保留实现 + 清理留痕 |
| D9 | 依赖 `mvn test` | 离线自检 + 端到端验收双轨 |
| D14 | 压测组数未定 | 必须含「全开 + 落盘」组 |

**评审结论**：修正后方案自洽，可以进入实施。若 D1/D2/D3 不修，整改会变成「换了代码但保留了原缺陷」。
