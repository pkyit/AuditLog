# 11 - 异步采集验证与跨机压测

**背景**：`docs/10` 明确列出两个未完成的验证缺口：
① 异步路径没有自动化测试；② spill 之后的稳态没有重新压测。
本轮用第二台服务器（`10.10.10.102`）补上了这两块。

**两台机器的角色**：
- `10.10.10.103`（openEuler，6C）：运行被测应用；
- `10.10.10.102`（Anolis 8.10，8C）：发起负载。**注意它同时是生产 CI 机器**
  （Jenkins + Superset），因此压测全程受控、并发降到 100、且确认 Jenkins 空闲后才执行。

## 一、异步采集：发现并修复一个真实缺陷

### 1.1 我上一轮的修复是不完整的（实测打脸）

`docs/10` 里我声称 H1 已修复。本轮把异步端点补上后**实测发现它没修好**：

| 断言 | 修复前 | 期望 |
|---|---|---|
| `durationMillis`（800ms 异步请求） | **1~2ms** | ≥700ms |
| 13 次请求的记录数 | **14 条** | 13 条 |
| 异步 POST 请求体 | 未采集 | 已采集 |
| 已标注异步端点 `operation` | **null** | 有值 |

### 1.2 根因

`AuditLogServletFilter.doFilterInternal` 在 **ASYNC dispatch 时会再执行一遍**，
而它无条件调用 `captureService.begin(request)` —— `begin()` 每次都创建**全新的上下文**
（新的 `eventTime`、空的 builder）。后果：

1. `durationMillis` 从第二次进入开始算 → 800ms 记成 1~2ms；
2. 语义通道在 ASYNC dispatch 又填一遍 → 与首次发布叠加成两条记录；
3. 首次捕获的请求体/操作名丢在旧上下文里 → 请求体与 `operation` 为空。

**诊断依据**（加了临时探针后的真实输出，修复前）：

```
[诊断-filter] uri=/async/callable dispatcherType=REQUEST isAsyncStarted=false hasCtx=false
[诊断-filter] uri=/async/callable dispatcherType=ASYNC   isAsyncStarted=false hasCtx=true   <- 两次进入
[诊断-finalize] uri=/async/post-callable dispatch=REQUEST status=200 elapsed=10ms
[诊断-finalize] uri=/async/post-callable dispatch=ASYNC   status=200 elapsed=192ms
```

### 1.3 修复

ASYNC dispatch **不再新建上下文**，改为复用首次暂存的上下文，只做收尾：

```java
boolean asyncDispatch = request.getDispatcherType() == DispatcherType.ASYNC;
if (asyncDispatch) {
    Object stored = request.getAttribute(ASYNC_CONTEXT_ATTR);
    Object storedRequest = request.getAttribute(ASYNC_REQUEST_ATTR);
    // 收尾时优先用**被包装的原始请求**：请求体缓存在它身上，
    // ASYNC dispatch 的新 request 对象拿不到
    HttpServletRequest payloadSource =
        storedRequest instanceof HttpServletRequest original ? original : request;
    chain.doFilter(request, response);
    if (stored instanceof AuditRecordContext deferred) {
        finalizeNow(deferred, payloadSource, response, businessError);
    }
    return;
}
```

两个关键点：
- **必须复用上下文**，否则耗时/请求体/操作名全部丢失；
- **必须把被包装的请求一起带过去**：ASYNC dispatch 拿到的是**新的 request 对象**，
  它不再是 `CachedBodyHttpServletRequest`，不传就采不到请求体（这正是我第一版修复漏掉的）。

### 1.4 验证结果（30/30 通过）

`tools/remote/35-run-async.py`（黑盒：真实 HTTP + 真实落盘记录）：

| 类别 | 结果 |
|---|---|
| 逐 URI 对账 | 12 个异步端点，记录数 == 客户端成功次数（**无重复、无漏记**） |
| **耗时** | 800ms 异步请求记录 **805ms / 804ms / 803ms** |
| **状态码** | `callable-500`→500、`callable-404`→404、`deferred(500)`→500（不再是占位 200） |
| 异步异常 | `outcome=FAILURE`、`error.type=jakarta.servlet.ServletException` |
| DeferredResult 超时 | 产生 1 条记录（**超时也不丢**） |
| 异步 + 请求体（已标注） | `{"orderId":"A-1","password":"******"}` —— 已采集且已脱敏 |
| 已标注异步端点 | `operation=异步-Callable-已标注` |

### 1.5 并发下"恰好一条"的确定性证明

单独做了并发专项（`tools/remote/37-async-concurrency.py`）：

```
顺序 20 次 -> 记录数 = 20
并发 20 次 -> 记录数 = 20
合计 40 = 客户端成功 40
结论: 没有多余记录（并发下也恰好一条）
```

### 1.6 顺带确认的一个设计属性（此前没写清楚）

**边界通道只记录元信息（方法/URI/状态码/耗时），不采集请求体**。实测对照：

```
/load/echo (同步 POST，未标注)          request={"contentType":"none","body":null}
/async/post-callable (异步 POST，未标注) request={"contentType":"none","body":null}
/async/post-annotated (异步 POST，已标注) body='{"orderId":"A-1","password":"******"}'
```

载荷采集是**语义通道**的职责。这一点很重要，因为它意味着
`max-cached-body-bytes`（64KB）与请求体脱敏只对带 `@AuditLog` 的端点生效；
未标注端点的边界记录**天然不含载荷**，也就没有"请求体泄漏"的风险面。

## 二、跨机负载压测（由 102 打向 103）

### 2.1 为什么要跨机

此前所有压测都是**应用与压测工具抢同一台 6C 机器**，还踩过"两个压测脚本同时跑、
互相污染"的坑（`docs/07` §4.4）。跨机后应用独占 103 的 CPU，测量更干净。

**压测端隔离**：102 是生产 CI 机器，因此
① 执行前确认 Jenkins 空闲（load 0.20）；
② 并发限制在 100、负载工具只占 2 核；
③ 压测后核对 Jenkins 无异常。

### 2.2 结果

`wrk -t4 -c100 -d60s`，应用绑 103 的 0-3 核：

| 场景 | req/s | P50 | P99 | collect | journaled | **dropped** |
|---|---|---|---|---|---|---|
| A 采集全开（默认队列） | **3,606** | 11ms | 493ms | 244,082 | 0 | **0** |
| B 采集全开 + 小队列强制 spill | **3,496** | 12ms | 526ms | 229,087 | 1,992 | **0** |
| C 异步端点（Callable 60ms） | 132 | 743ms | 782ms | 10,072 | 0 | **0** |

### 2.3 这三组数字说明什么

**1）跨机与单机结果一致 → 单机实验没有被压测工具污染。**
同口径（4 线程 / 100 连接 / 60s）对比：

| | 单机（103 同时跑应用与 wrk） | 跨机（102 打向 103） |
|---|---|---|
| 采集全开 req/s | 3,003 | **3,606** |
| P50 | 58ms | **11ms** |

跨机后吞吐略高、P50 明显更低。**结论**：此前的瓶颈是应用自身（采集路径），
不是压测工具抢占；单机实验的结论方向是可信的。

**2）spill 路径不再拖垮吞吐（M1 修复的实测价值）。**
场景 B 强制溢出：队列压到 2048、批次 50，`journaled=1,992`、`backpressure=1,992`
（两者相等说明确实是"队列满"触发的背压，符合队列容量 2048）。
而吞吐只从 3,606 掉到 3,496（**-3%**），P99 从 493ms 到 526ms。

对比 `docs/07` §4 记录的旧行为：旧实现下 `updateDepthGauge()` 每次成功入队都会
调用 `FileAuditJournal.pendingCount()`，而它**遍历所有 WAL 分段做行数统计** ——
一旦发生过 spill，**每个请求的入队都要付全量 WAL 行扫描的 I/O**。
现在 `pendingCount()` 是纯内存读（`onDiskLines` 计数器），因此 spill 稳态不再有额外开销。

> **诚实说明**：我**没有**用旧代码在这台跨机环境上重跑 B 场景做直接对照，
> 因此不能给出"M1 带来了 X% 提升"的数字。这里能说的是：
> ① spill 稳态下吞吐仅降 3%，没有出现"每请求扫 WAL"应当造成的量级劣化；
> ② M1 把该路径从"每次入队 O(分段行数) I/O"改成"内存计数器"，这是代码层面的事实。

**3）`dropped=0` 在两组高压场景下都成立，且账目对得上。**
场景 A：`collect 244,082 = delivered 244,082`。场景 B：溢出的 1,992 条走了本地兜底日志
（`journaled=1,992`），因此 `collect 229,087 - delivered 227,095 = 1,992` —— **一条不差**。

**4）异步端点在这个测试下是端点受限，不是框架受限。**
132 req/s 看起来很低，但 `delayMillis=60` 的异步请求实测耗时约 750ms
（60ms 业务延迟 + 异步派发 + 审计收尾），100 连接下 `100 / 0.75s ≈ 133 req/s` —— 与实测吻合。
所以**这个数字反映的是端点服务时间，不是框架吞吐上限**。
它的价值在于：在 100 并发异步压力下，记录数 10,072 条、**dropped=0**，
说明高并发异步路径不会丢记录、不会重复发布。

### 2.4 对生产 CI 机器的影响（如实核对）

压测后 102 状态：

```
load average: 0.36, 0.70, 0.56
jenkins      CPU 0.12%   MEM 556.9MiB
superset_app CPU 0.03%   MEM 229.6MiB
```

Jenkins 日志中的错误是**既有的** Kubernetes client 无法连接 `kubernetes.default.svc`
（每 5 分钟重试一次），与本次压测无关，压测前后都存在。

### 2.5 顺带发现：102 上 Superset 的两个容器长期崩溃（与本次压测无关）

清理时注意到 `superset_worker` 与 `superset_worker_beat` 处于重启循环。
**已核实与本轮压测无关**，证据如下：

| 证据 | 值 | 说明 |
|---|---|---|
| `RestartCount` | **2389** | 容器创建于 **6 周前**，即约 5.7 次/小时，已持续数周 |
| 崩溃原因 | `ModuleNotFoundError: No module named 'superset.tasks.deletion_retention'` | 镜像与代码版本不匹配，启动即失败 |
| 内核日志 | 无 OOM 记录 | 不是资源问题 |
| `superset_app` / `jenkins` | Up 9 小时 / Up 45 小时，均健康 | 压测期间未受影响 |
| 压测前后 | 同样处于 Restarting | 状态未变化 |

**未做处理**：这是使用者自己的生产环境问题（且涉及镜像版本决策），
不在本次任务范围内，改动他人环境风险高于收益。仅如实报告。
**建议**：`superset_worker` 与 `superset_worker_beat` 所用的镜像版本与代码不匹配
（缺少 `superset.tasks.deletion_retention` 模块），需要对齐版本后重启；
`superset_app` 本身是健康的，因此影响面主要是异步任务与定时任务不执行。
