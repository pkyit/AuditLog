# 性能验证方案

> **动机**：原设计文章用一次压测（`wrk -c 1000 -t 12 -d 30s`，18,152 QPS）来证明
> "选择 Spring MVC 扩展机制而非 AOP 的正确性"。但那个端点把三个采集开关**全部设为 false**：

```java
@AuditLog(name = "查询用户信息3", logHeaders = false, logRequestParams = false, logResponseParams = false)
```

因此压测只执行了 `map.containsKey()` + `new AuditLogEvent()` + `publishEvent()`，
**采集逻辑（脱敏遍历、参数序列化、响应序列化）一行都没执行**。
用它证明"框架性能"没有测到框架的真实成本。本方案用于把这件事测准。

---

## 1. 必须测的组（四组对照 + 一组存储）

| 组 | 配置 | 测的是什么 |
|---|---|---|
| **G0 基线** | 完全不带审计（对照应用或关闭 `audit.log.enabled`） | 业务接口自身的性能上限 |
| **G1 AOP 对照** | 用 `@Around` 实现同样的采集 | 回答"是否真的比 AOP 快" |
| **G2 采集全关** | `@AuditLog` 存在但三开关全 false | 复现原文章的测法（**仅作对照，不代表能力**） |
| **G3 采集全开 + 内存存储** | headers/request/response 全开，store=in-memory | 采集 + 脱敏 + 序列化的真实成本 |
| **G4 采集全开 + 落盘** | 同上，store=json-file | **生产最接近的真实成本**（含磁盘 I/O） |

**结论只允许从 G4 得出**。G2 的数字只能用于说明"关掉采集后确实很快"，不能用来宣称框架性能。

## 2. 指标要求（缺一不可）

- **吞吐**：QPS（稳定段平均，剔除预热与尾段）
- **延迟分布**：P50 / P95 / **P99 / P999**（平均值会掩盖尾延迟）
- **错误率**：非 2xx 比例
- **资源**：CPU 使用率、**GC 次数与停顿**（`-Xlog:gc*`）、堆水位、线程数
- **审计链路自身**：
  - `audit.pipeline.queue.depth` 曲线（是否持续增长 → 消费能力不足）
  - `audit.store.latency.sum/count/max`（存储投递耗时）
  - `audit.pipeline.backpressure` / `journaled` / `dropped`（背压是否触发、是否丢数据）
  - `audit.pipeline.journal.pending`（WAL 是否在积压）

## 3. 压测方法

### 3.1 环境要求

- 压测机与被测机分离（避免压测工具自身争抢 CPU）；
- 明确并记录：CPU 核数、内存、JDK 版本与 GC、磁盘类型、网络；
- 每组**预热 ≥ 60s**，测量 ≥ 300s；
- 每组重复 3 次，取中位数，并报告离散度。

### 3.2 负载配置（不要只测一个并发）

| 场景 | 并发 | 说明 |
|---|---|---|
| 低负载 | 50 | 观察框架固定开销占比 |
| 中负载 | 200 | 常态 |
| 高负载 | 500 | 接近容量 |
| 过载 | 1000 | **观察背压策略是否按预期工作**（重点） |

### 3.3 接口选择（必须覆盖不同采集成本）

| 接口 | 特点 | 为什么必须测 |
|---|---|---|
| `GET /user/queryUserInfo` | 无请求体，小响应 | 基线固定开销 |
| `GET /user/queryUserInfo3` | 原压测端点（开关全关） | 与原结论对比 |
| `POST /user/create` | **有请求体 + 敏感字段脱敏** | 脱敏成本（生产主要成本之一） |
| 大报文接口（自建，如 100KB JSON） | 大载荷截断 | 验证 `max-body-length` 与截断逻辑的成本 |
| 列表接口（返回 1000 条） | 大响应 | 验证响应侧成本（注意：默认不采响应正文） |

### 3.4 命令示例

```bash
# 建议使用支持延迟分布输出的工具
wrk -c 500 -t 12 -d 300s --latency -s report.lua http://HOST:8083/user/queryUserInfo?userId=perf

# 或使用 k6 以获得 P99/P999 与阶段化负载
k6 run --vus 200 --duration 300s scenario.js
```

> 注意：`wrk` 默认只输出平均延迟，**无法回答尾延迟问题**。请使用 `--latency`
> 或改用 `k6` / `JMeter`。

## 4. 结果记录模板

| 组 | 并发 | QPS | P50 | P95 | P99 | P999 | 错误率 | CPU | GC 停顿 | 队列深度峰值 | dropped | journaled |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| G0 |  |  |  |  |  |  |  |  |  | — | — | — |
| G1 |  |  |  |  |  |  |  |  |  |  |  |  |
| G2 |  |  |  |  |  |  |  |  |  |  |  |  |
| G3 |  |  |  |  |  |  |  |  |  |  |  |  |
| G4 |  |  |  |  |  |  |  |  |  |  |  |  |

**必填结论**：

1. 采集全开相对基线的**开销占比**（G4 vs G0）；
2. 与 AOP 实现的**对照差异**（G4 vs G1），并说明是否具有统计意义；
3. **过载组**是否出现 `dropped > 0`；若出现，说明背压策略与容量需要调整；
4. 队列深度是否稳定（持续增长 = 消费能力不足）；
5. GC 是否因审计对象（快照、批次列表）产生新的压力。

## 5. 反模式清单（评审时会直接质疑这些做法）

| 反模式 | 为什么站不住 |
|---|---|
| 只测关闭采集的端点 | 没有测到采集成本（原文章的问题） |
| 只报告平均延迟 | 掩盖尾延迟，而 SLA 通常看 P99 |
| 只报告 QPS 不报告错误率 | 高 QPS 可能来自大量快速失败 |
| 无 AOP 对照就宣称"比 AOP 快" | 缺少对照，结论无依据 |
| 压测机与被测机同机 | 压测工具与业务争抢 CPU，数字不可用 |
| 只测 30 秒 | 未进入稳态，JIT 与 GC 均未稳定 |
| 用本机 wrk + 1000 长连接 | 瓶颈常在连接排队而非被测代码 |
| 不报告 `dropped` | 用"丢数据"换来的吞吐不能用于宣称可靠性 |

## 6. 预期与定位

基于本实现的设计，可以预期的定性结论（需用上述方法**实测验证**，不要直接引用）：

1. 采集全开的成本主要来自**脱敏与序列化**，而不是"在不在 AOP"；
2. 相比 AOP 的差异可能落在个位数百分比区间 —— 因此**性能不应作为选择本框架的首要理由**；
3. 本框架真正的价值在于**不变量**（身份可信、结果真实、不丢、可验），而不是省下那几毫秒；
4. 背压与 WAL 的作用在**过载组**才会体现：业务延迟不因审计存储故障而雪崩，且数据不丢。

如果实测显示 G4 相对 G0 的开销不可接受，正确的调整顺序是：

1. 降低采集深度（关 `logRequestParams`、缩小 `max-body-length`）；
2. 增大 `queue-capacity` 与批量；
3. 更换更快的存储（如 MQ）；
4. **而不是**退回"记录不可信"的实现。
