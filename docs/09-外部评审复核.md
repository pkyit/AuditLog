# 09 - 外部评审报告的独立复核

**背景**：收到一份外部（GLM）全面代码评审报告 `08-全面代码评审报告.md`，
对当前版本给出 7.5/10，并列出 1 个致命缺陷 + 3 个高优先级 + 5 个中优先级 + 8 个打磨项。

**本文的立场**：**逐条独立复核，不因为"是别人提的"就接受，也不因为"是别人提的"就排斥。**
每条结论都标注了验证方式与证据。

**复核方法**：读代码定位 + 写测试固化 + 在真实服务器上用 HTTP 请求实测。
凡是我无法独立确认的，明确标注"未验证"，不给出倾向性判断。

## 二、C1 复核详情（最重要的一条）

### 2.1 报告的说法

`CachedBodyHttpServletRequest.wrap()` 最多读 `maxCachedBodyBytes`（默认 64KB）就停止，
未消费剩余字节；而包装后的 `getInputStream()` 只返回已缓存字节。
于是 POST/PUT/PATCH/DELETE 且请求体 > 64KB 时，**下游业务读到被截断的报文**。

### 2.2 我的实测（真实 HTTP，不是静态推导）

在 `demo` profile（`max-cached-body-bytes` 保持默认 64KB）下，
用一个回显"业务真正收到的字节数 + SHA-256"的接口做对照：

**修复前**：

| 发送字节 | 业务收到 | SHA 一致 | HTTP | 结论 |
|---|---|---|---|---|
| 1,000 | 1,000 | 是 | 200 | 完整 |
| 60,000 | 60,000 | 是 | 200 | 完整 |
| 65,536 | 65,536 | 是 | 200 | 完整 |
| **70,000** | **65,536** | **否** | 200 | **被截断** |
| **200,000** | **65,536** | **否** | 200 | **被截断** |
| **1,000,000** | **65,536** | **否** | 200 | **被截断** |

**C1 完全成立。** 而且比报告描述的更严重一点：

1. **不是"大报文"才有问题 —— 只要 `content-length != 0` 就会被包装**，
   所以限额是 64KB，不是 2MB。所有超过 64KB 的写请求都中招；
2. **HTTP 状态码是 200** —— 客户端不知道自己的数据被丢了，属于**静默数据损坏**。

### 2.3 我当时为什么没测出来（诚实说明）

我的安全测试里有一条"3MB 报文 → 连接被拒（Tomcat `maxPostSize`）"，
我把它记为"通过"。但我**只测了 3MB 这一个点**，而 Tomcat 的 `maxPostSize` 是 2MB ——
3MB 在容器层就被拒了，**根本没进到审计过滤器**。
真正的缺陷区间是 **64KB ~ 2MB**，而我的压测载荷是 320 字节、安全测试载荷是 148 字节，
**恰好整个区间都没覆盖**。

**教训**：验证边界时，"取两个极端点"是不够的；必须覆盖**阈值附近**（`64KB±`、`2MB±`）。
这也是我这份实测报告的一个真实盲区。

### 2.4 修复与验证

采用报告的建议方案 1（tee：业务读原始流，审计旁路拷贝前缀）：

- 业务永远读到完整报文 —— 无论多大；
- 审计拿到前 `maxCacheBytes` 字节并标记 `truncated=true`；
- 内存占用仍有上限 —— 不会因为大文件上传而 OOM。

**修复后实测（同一脚本、同一机器）**：

| 发送字节 | 业务收到 | SHA 一致 | 结论 |
|---|---|---|---|
| 1,000 / 60,000 / 65,536 | 一致 | 是 | 完整 |
| **70,000** | **70,000** | **是** | **完整** |
| **200,000** | **200,000** | **是** | **完整** |
| **1,000,000** | **1,000,000** | **是** | **完整** |

**回归测试**：`CachedBodyHttpServletRequestTest`（9 个用例）锁死：
报文大于上限时业务必须读到完整内容（长度 + 摘要 + 逐字节相等）、
缓存恰好停在上限、标记 truncated、分块/单字节混合读取不丢字节、
业务只读一部分时审计拿到已读前缀、`wrap()` 兼容入口可重复读。
另有一个测试在修复过程中**真的抓到了我自己引入的回归**
（缓存复用同一个 `ByteArrayInputStream` 导致第二次读为 0 字节）——
这正是"回归测试必须覆盖重复读取语义"的价值。

## 三、对其余各条的复核要点

### C2（链 head 不持久化）—— 成立，且报告的分析是对的

`Sha256AuditChain`/`HmacAuditChain` 的 `head` 初始化为 `GENESIS` 且**不持久化**；
`AuditPipeline.deliver()` 在投递前调用 `chain.link(record)`，
重放路径也会再次 link。因此：
- **正常重启**：新记录 `prevHash=GENESIS`，与存储中上一条 `recordHash` 无法衔接；
- **崩溃恢复**：save 成功、checkpoint 之前崩溃 → 重放这批 → 以新 head 重新链接 →
  JDBC 主键幂等拒绝 → 整批进死信，且内存 head 已前进到"从未落库的哈希"。

报告还指出 `actuator` 的链校验只验内存 `recentRecords`，**发现不了这两种断裂**，
会给出"链完好"的假信号。这一点我在做防篡改攻防时也**没有意识到** ——
我当时验证的是"单进程内链自洽"，恰好绕过了这个盲区。

### H4（类级注解不生效）—— 成立，我用测试固化了事实

注解声明了 `@Target({METHOD, TYPE})` + `@Inherited`，
且 `ignore()` 的 javadoc 明说"用于在类级别开启后单独排除某方法"，
但 `populate()` 只做 `AnnotatedElementUtils.findMergedAnnotation(method, ...)`。

我没有靠"我认为 Spring 不向上查类"来下结论，而是写了一个测试断言这个事实：

```
方法级标注 -> 查得到（对照组，assertNotNull）
类上标注、方法未标 -> 查不到（assertNull）   <- 固化事实
类上标注 -> 在 Class 上查得到（assertNotNull）
```

测试通过，**H4 成立**。这个用例同时是修复后的验收标准。

### M1（热路径磁盘 I/O）—— 成立，且与我的性能报告直接冲突

`updateDepthGauge()` 在**每个成功入队分支**里调用，
而 `FileAuditJournal.pendingCount()` 会遍历**所有 WAL 分段**做 `Files.lines().count()`。

**这与我在 `docs/07` 里的结论直接相关**：我测出"采集全开吞吐约为基线的 11%"，
但**我的压测从头到尾没有触发过 spill**（`dropped=0`、队列未满）。
一旦发生过 spill，分段文件在重放+保留清理之前一直存在，
那么**每个请求的入队都会付出全量 WAL 行扫描的 I/O** —— 这是我完全没测到的劣化路径。
报告的这条比我的性能测试更全面。

### M3（链未覆盖归属字段）—— 成立，影响面比报告说的更大

`canonicalContent()` 不含 `clientIp`、`queryString`、`userAgent`、`tags`、
`serviceName`、`instanceId`、`principalName`、`sessionId`、`error.message`。

我在做防篡改攻防时验证了"篡改 outcome 会被检出"，但**没有验证"篡改 clientIp 会不会被检出"**。
按报告的推导：对 HMAC 链（攻击者无密钥），拥有存储写权限者**直接改写 clientIp/queryString/UA
不会破坏校验**。对审计取证而言这恰是最需要防篡改的字段。这是有效发现。

### M5（order=-100 与 Spring Security 相同）—— 值确认，顺序影响未实测

`Boundary.order` 默认 `-100` 已确认；Spring Security 的 `springSecurityFilterChain`
注册 order 默认同样是 `-100`。**同值不保证先后**这一点是成立的。

若审计过滤器排在 Security 之后，未认证请求在 Security 层被拦截时不经审计过滤器，
**认证失败事件漏采** —— 这恰恰是边界通道存在的首要理由。
我**没有实测这个顺序**（samples 未引入 Spring Security），
所以我把结论限定为"值相同导致的顺序不确定性成立，实际是否翻转未验证"。

### L2 / L3 —— 抽样复核成立

- **L2**：`JsonFileAuditStore.save` 用 `line.length()+1`、`FileAuditJournal.writeRecord` 用
  `line.length()` 做字节数统计 —— 按 `char` 而非 UTF-8 字节计，
  中文内容下轮转阈值系统性偏小。成立。
- **L3**：`shouldNotFilter` 用 `AntPathMatcher`，而默认排除模式是 `*.css` 这类。
  Ant 的 `*` **不跨目录分隔符**，因此 `/static/app.css` 不会被排除。成立。

## 四、方法论反思：为什么这次静态评审赢了我的动态测试

**我漏掉 C1，不是因为不认真，而是因为方法本身有盲区。**

| | 我做的（动态测试） | GLM 做的（静态通读） |
|---|---|---|
| 强项 | 能证明"跑起来确实是这个数"、能发现真实运行才暴露的问题（如 NPE、指标翻倍、丢数据） | **覆盖所有代码分支**，包括我没构造出的输入 |
| 盲区 | **只能覆盖我构造的输入** —— 我的载荷是 148/320 字节，恰好避开了 64KB~2MB 区间 | 无法确认影响面与是否真的触发，需要动态验证补强 |

**结论**：两者不可互相替代。
- 我的 4 个"真实缺陷"（NPE、`canonicalContent` 的 `"null"`、指标翻倍、退避被中断）都是**静态评审很难发现**的；
- GLM 的 C1 是**动态测试很难发现**的（除非恰好构造了阈值附近的输入）。

**这次得出的最重要的工程教训**：**测试用量的选择本身就是一种风险**。
我用同一个 320 字节载荷做了 6 组压测、跑了几十万次请求，
却没有一次请求体超过 64KB —— 于是把一个"所有大报文写操作全部损坏"的缺陷
完美地藏在了测试盲区里。
