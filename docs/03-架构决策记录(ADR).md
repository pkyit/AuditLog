# 架构决策记录（ADR）

本文件记录审计框架在整改过程中做出的关键取舍。每条 ADR 包含：**决策、背景、被否决的方案、代价**。
架构评审最容易遗漏的正是"代价"一栏，因此这里强制写出。

---

## ADR-001：采集挂载点选择 —— 双通道而非单一挂载

**状态**：已采纳

**背景**：原实现把采集挂在 `ServletInvocableHandlerMethod#doInvoke`。
优点是精确、开销小；缺点是**只有进入方法体才采集**，
于是认证失败、401/403、限流熔断、参数绑定失败、404 这些最有审计价值的安全事件全部漏采。

**决策**：采用双通道。

- **边界通道**（`OncePerRequestFilter`，order = -100，早于 Spring Security）：
  建立唯一审计上下文、覆盖全部请求、在 `afterCompletion` 用真实状态码发布记录。
- **语义通道**（`WebMvcRegistrations` → `AuditLogHandlerMethod`）：
  只往同一上下文里补操作名、动作类型、资源 ID、耗时与事务结果，**不发布**。

**被否决的方案**：

| 方案 | 否决原因 |
|---|---|
| 只用 Filter | 拿不到操作名、资源 ID、动作类型等审计语义，退化为 access log |
| 只用 HandlerAdapter（原方案） | 漏采全部未进入方法体的事件（含最关键的认证/授权失败） |
| AOP 环绕通知 | 同样漏采未进入方法体的事件；且与响应式栈、内部调用不友好 |
| 两个通道各发一条记录再按 requestId 合并 | 异步下顺序不确定，粗粒度记录可能覆盖语义记录，**会丢掉审计语义** |

**代价**：

- 语义通道依赖 `WebMvcRegistrations`，与宿主或其他框架组件**互斥**（同容器仅一份生效）。
  缓解：语义通道可整体关闭，被覆盖时仅语义字段缺失，**边界通道仍保证不漏事件**（明确降级）。
- 请求体需要缓存（`CachedBodyHttpServletRequest`），有内存成本，已用 `max-cached-body-bytes` 限制。

## ADR-002：一条记录两阶段填充，而非两条记录事后合并

**状态**：已采纳（整改方案自评审 D1 的修正）

**背景**：整改方案初稿提出"边界记录 + 语义记录，用 requestId 关联并覆盖"。

**决策**：**一条记录、两个阶段填充、边界通道唯一一次发布**。
`AuditRecord.Builder` 可变但只在请求线程内使用，请求结束时冻结为不可变 `AuditRecord`。

**为什么否决"事后合并"**：
语义记录经有界队列异步到达存储，边界记录在 `afterCompletion` 产生，两者**到达顺序不确定**。
"覆盖"可能变成"被覆盖"，最终留下粗粒度那条 —— 恰好丢掉审计最需要的操作名与变更快照。
若在内存中建关联表，则重新引入跨请求共享可变状态、内存泄漏与锁竞争。

**代价**：语义通道不再独立发布，若它被禁用/被覆盖，就没有"第二份记录"兜底。
这是**有意选择**：宁可要一条完整记录，也不要两条不确定关系的记录。

## ADR-003：事务结果对齐 —— 回滚默认不产生记录

**状态**：已采纳（自评审 D3 的修正）

**背景**：原实现在 `finally` 中同步发布事件，而事件产生于业务事务**提交之前**，
因此业务回滚时审计仍记录"成功"。这是审计最严重的一类错误：**记录了没有发生的事**。

**决策**：

- 通过 `TransactionSynchronization` 在 `afterCompletion` 捕获真实事务结果并写回上下文；
- 默认 `audit.log.drop-on-rollback=true`：**事务回滚不产生审计记录**；
- 需要审计"尝试性操作"时设为 `false`，记录会带 `Outcome=ROLLBACK` + `rolledBack=true`，
  消费方必须理解为"尝试未生效"。

**为什么默认 DROP 而不是一律记 ROLLBACK**：
回滚意味着"什么都没发生"。为一次未生效的操作留一条记录，
在合规结论上会污染事实（"管理员删除了用户 X"但事务已回滚）。

**代价**：**放弃了对"失败尝试"的默认可见性**。需要该能力必须显式开启，
且消费方需理解 `ROLLBACK` 语义。这是有意的显式化，而不是替使用者猜测。

## ADR-004：背压默认 SPILL，而不是 BLOCK 或丢弃

**状态**：已采纳

**背景**：队列打满时，"审计不丢"与"业务 SLA 不降"必然冲突。框架不能假装冲突不存在。

**决策**：提供五种策略，默认 `SPILL`（队列满时降级写本地 WAL，独立写线程，不阻塞业务；存储恢复后重放）。

**被否决的方案**：

| 方案 | 否决原因 |
|---|---|
| Spring 默认 `@Async` 无界队列 | 压力转化为内存堆积，最终 OOM |
| `CallerRunsPolicy` | 让**业务线程**去执行落库/发 MQ，把审计开销直接压回业务 SLA（原实现注释里正是这个） |
| 直接丢弃 | 审计数据真实丢失，与"不丢"目标矛盾 |
| 默认 BLOCK | 审计消费能力不足会直接拖慢业务接口 |

**代价**：需要磁盘空间；WAL 自身也可能饱和。
因此设置三级降级并**全部计数**：队列 → WAL 队列 → 内存缓冲 → 丢弃 + 告警。
最末级的 `audit.pipeline.dropped` 必须配置告警。

**WAL 写入刻意不在业务线程做磁盘 I/O**：`append()` 只入有界队列，由专属写线程落盘，
否则 SPILL 自己会变成新的阻塞点（自评审 D5）。

## ADR-005：脱敏在请求线程内完成，入队即已脱敏

**状态**：已采纳

**背景**：异步线程处理时，请求对象已失效、实体可能已脱管。

**决策**：脱敏与序列化全部在**请求线程内**完成，进入队列的是不可变、已脱敏的快照。

**代价**：请求线程承担序列化 + 脱敏开销（这是审计的真实成本所在）。
缓解：只有被 `@AuditLog` 标注的请求才做深度采集；未标注请求仅采集来源与结果。

**同时的决定**：默认**不序列化方法实参**（`serialize-arguments=false`），
改用缓存的请求体/查询串生成结构化快照。
理由：序列化任意 Java 实参是原实现最危险的举动（懒加载异常、循环引用、超大对象、框架参数噪音）。

## ADR-006：字段路径用段匹配，不把 glob 编译成正则

**状态**：已采纳（实施期发现的缺陷修正）

**背景**：初版把 `$.token` 编译为锚定正则 `(?i)^\$\.[^.\[\]]+token$`，
结果是它**无法匹配** `$.nested.token`。

**决策**：实现 `FieldPathMatcher`，把 glob 与路径都切成**段**，用带 `**` 回溯的动态规划匹配。
语义：未书写 `**` 的规则表示"任意层级上出现该名字"（配置 `$.token` 的意图显然如此）；
字段名比较大小写不敏感。

**为什么这条 ADR 值得单独记录**：该缺陷的表现是
**"配置了敏感字段却依然原文落库"** —— 一种**静默的数据泄漏**，
且单元测试若只覆盖单层路径就完全测不出来。审计框架里这类"配置看起来生效、实际不生效"的问题
危害远大于显式报错。它同时说明：安全相关的匹配逻辑不应依赖正则的边界技巧，应当语义可读、可测。

## ADR-007：哈希链默认关闭；无密钥链的能力边界必须写明

**状态**：已采纳

**背景**：防篡改有性能成本，且有密钥管理成本。

**决策**：

- `chain.enabled` 默认 `false`，但启动时告警"审计历史可被有写权限者静默修改而无法察觉"；
- 开启但未配 `secret` 时，使用无密钥 SHA-256 链，并**明确告警其能力边界**：
  能发现意外损坏与无密钥篡改，**不能抵御拥有写权限的攻击者**（对方可重算整条链）；
- 提供 `HmacAuditChain`（密钥不落存储侧）与 `constantTimeEquals`（避免比较耗时侧信道）。

**代价**：链是**有状态串行结构**。多消费者并发链接会导致 `prevHash` 分叉、链校验必然失败。
框架的处理是在 `Config` 构造时**强制把消费者降为 1**（而不是产生一条坏链），并记录告警。

## ADR-008：哈希链的"锚定"责任交给使用者

**状态**：已采纳

**背景**：即使有 HMAC，若攻击者能改记录**同时**拿走密钥（例如密钥与应用同机），链仍可被重算。

**决策**：框架提供 `AuditChain#currentHead()` 作为锚点，但不内置外部锚定实现
（需要对象存储 WORM / 区块链 / 可信时间戳等外部系统）。
文档明确说明：**要真正抵御有写权限者，必须把链头定期锚定到外部不可变存储**。

**代价**：开箱不提供"完全防篡改"，这是一个**需要使用者参与**的能力。
刻意不夸大：把"能发现意外损坏"宣传成"防篡改"是审计产品里最常见的误导。

## ADR-009：方法级元数据在容器刷新后填充（避免循环依赖）

**状态**：已采纳（实施期修正）

**背景**：注册表需要 `RequestMappingHandlerMapping`，但在 Bean 创建阶段注入它会**提前触发 WebMvc 自动配置**，
而 WebMvc 又依赖本框架的 `WebMvcRegistrations` → 采集服务 → 注册表，形成循环依赖，应用无法启动。

**决策**：`AuditMethodRegistry` 在 Bean 阶段为空；由 `AuditLogStartupValidator`
在 `SmartInitializingSingleton#afterSingletonsInstantiated` 中填充（此时 WebMvc 已完成初始化）。

**代价**：注册表在应用启动早期是空的。若有组件在更早阶段读取它，会看到空集合。
当前所有读取方（采集服务在请求期、端点在校验后）都晚于填充时机，因此安全。

**同时修正**：不能依赖 `getIfUnique()` 获取映射 —— 引入 Actuator 后会多出
`controllerEndpointHandlerMapping`，导致返回 `null`、注册表为空、**注解全部静默失效**。
改为按 Bean 名 `requestMappingHandlerMapping` 优先、其次按类型确定性选取。

## ADR-010：不提供"审计与业务同事务写入"

**状态**：已采纳（自评审 D2 的修正）

**背景**：整改方案初稿曾计划提供 `commitMode=REQUIRED_SAME_TX`。

**决策**：**删除该模式**。只保留 `EVENTUAL` 与 `AFTER_COMMIT` 两种语义。
`AuditStore` 增加 `supportsSameTransaction()`，**由存储实现自行声明**是否具备该能力。

**为什么否决**：同事务写入与异步流水线在设计上互斥 ——
一旦要求同步写库，背压、队列、WAL、批量全部失效，
且**业务事务被审计库的可用性绑架**（审计库挂 → 业务全挂）。
这是一个危险且自相矛盾的承诺，不应由框架默认提供。

**代价**：开箱不支持强一致审计。确需者必须在自定义 `AuditStore` 中自行实现，
并自行承担"审计可用性即业务可用性"的后果。

## ADR-011：默认存储为 `logging`，但必须显式告警

**状态**：已采纳

**背景**：审计日志需要独立留存；若默认写应用日志，会随日志滚动被删除。

**决策**：默认 `store.type=logging`（引入依赖不破坏使用者环境），
但启动校验**必须打印告警**说明其不满足合规留存要求。

**代价**：默认配置不符合合规要求。这是"默认不破坏环境"与"默认合规"之间的取舍，
选择了前者 + 显式告知，而不是替使用者默认写文件或写库。

## ADR-012：验收方式 —— 应用内端到端验收入口

**状态**：已采纳（环境约束驱动）

**背景**：开发环境离线，本地 Maven 仓库中 surefire 及其传递依赖只有空目录、没有 jar，
`mvn test` 无法执行。

**决策**：双轨验证。

1. **单元测试**：保留标准 JUnit 5 测试源码，并提供 `tools/run-tests.ps1` +
   `JUnitConsoleRunner`，直接通过 **JUnit Platform Launcher** 执行
   （与 surefire 跑的是同一套引擎）。联网环境加回 `maven-surefire-plugin` 即可用
   `mvn test` 获得同样结果，测试源码零改动。
2. **端到端验收**：`demo` profile 启动后用真实 HTTP 请求跑完 11 项断言，
   以退出码反映结果（可直接用于 CI）。

**为什么这个选择其实是加分项**：单元测试锁住了**曾经出过真实缺陷**的算法
（字段路径匹配、脱敏、队列、哈希链、流水线可靠性），端到端验收则覆盖了
**真实 HTTP 链路、真实 Spring MVC 扩展点、真实事务、真实存储降级路径**。

**代价**：需要维护一个 ~150 行的测试启动器；验收需启动完整应用（约 30 秒）。

## ADR-013：指标归属约定 —— 同一事件只能被计数一次

**状态**：已采纳（实施期由测试发现真实缺陷后确立）

**背景**：单元测试发现 `audit.store.deadletter` 被计成两倍
（17 条死信计成 34），原因是 `AuditPipeline.deadLetter()` 与
`FileAuditJournal.appendDeadLetter()` **都**递增同一个指标。
同类问题还存在于 `audit.pipeline.dropped`。

**为什么这是严重问题**：审计框架的可靠性**只能靠指标证明**。
指标一旦翻倍或漏计，就再也无法从数据上区分"没丢"与"丢了一半"——
"不丢数据"这个核心不变量会退化为一句口号。这比崩溃更危险，因为它是静默的。

**决策**：确立单一归属原则，并在代码中写明：

| 指标 | 唯一负责人 | 理由 |
|---|---|---|
| `audit.pipeline.dropped` | `AuditPipeline` | 只有它知道被拒之后是丢弃、还是走了别的兜底路径 |
| `audit.store.deadletter` | `AuditPipeline` | 同上；`AuditJournal` 只用返回值暴露写入失败 |
| `audit.pipeline.journaled` / `journal.rejected` | `FileAuditJournal` | 属于"兜底日志自身"的状态 |
| `audit.store.delivered` / `store.failed` | `AuditPipeline` | 投递语义由流水线定义 |

**代价**：`AuditJournal` 的实现者不再自行计数，必须通过返回值表达成功/失败。
这是一次**接口契约的收紧**，换来的是指标可信 —— 值得。

## ADR-014：重试退避不可被中断放弃

**状态**：已采纳（实施期由测试发现真实缺陷后确立）

**背景**：单元测试（注入存储故障）稳定地只落下 17/20 条死信，缺的正是
停机瞬间正在重试的那一批。原因是重试退避用 `Thread.sleep`，
被中断时调用方选择 `break` 放弃剩余重试 —— 于是**整批记录既不投递也不落死信**，
在停机瞬间被静默丢弃。

**决策**：

1. 退避改用 `LockSupport.parkNanos`（不抛 `InterruptedException`），
   **坚持把重试走完**；停机安全性由 `stop()` 的 join + 最终 drain 负责；
2. 即使真的被中断，也必须**先落死信再退出**，绝不"直接 break 返回"。

**取舍说明**：这会让停机最多多等几百毫秒（走完退避）。
选择了**宁可慢一点，也不能丢审计数据** —— 这正是审计组件应有的取向。

**代价**：停机时间上界由 `maxRetries × retryBackoff` 决定，需要在配置时注意
（文档已说明）。
