# 优化方案：在保证审计要求的前提下降低采集开销

**背景**：`docs/06-实测报告.md` 测得采集全开时吞吐降至基线的 ~11%、P99 劣化 ~10 倍。
本文回答：**在不牺牲审计有效性的前提下，能优化什么、代价是什么、怎么验证。**

**方法论前置声明**：本文的优化不是"猜哪里慢"，而是先用 async-profiler
在负载下取火焰图，按**包含式调用链**定位真实热点，再改、再测。
期间我推翻过一次自己的判断（见 §5），也修掉了一个错误的性能结论（见 §1.3）。

---

## 1. 先定位：火焰图给出的真实热点

**方法**：应用绑 4 核、压测绑 2 核，`/load/full`（请求头 + 请求体 + 脱敏，JSON 载荷 180 字符），
`wrk -t4 -c200`，async-profiler 采 CPU（wall clock）与分配。

### 1.1 结果（包含式调用链，占该场景 CPU 的比例）

```
76.05%  AuditLogServletFilter.doFilterInternal            <- 审计过滤器整体
35.84%  └─ AuditCaptureService.finish
27.04%  └─ AuditCaptureService.begin
22.98%     └─ RuleBasedAuditMasker.maskQueryString
22.65%        └─ RuleBasedAuditMasker.applyRegexRules
22.53%           └─ java.util.regex.Matcher.find
```

### 1.2 结论：最大的单项开销是**内容正则的重复全量扫描**

`applyRegexRules` 的原实现是**每条规则各自完整扫描一遍文本**：

```java
for (RegexMaskRule rule : options.regexRules()) {   // 默认 5 条
    Matcher matcher = rule.pattern().matcher(result);  // 每条都从零扫
    ...
}
```

默认启用 5 条内置规则（Bearer 令牌、身份证、银行卡、手机号、邮箱），
于是一个 180 字符的值要跑 **5 遍**正则，而且每遍都新建 `Matcher` 与 `StringBuilder`。
在火焰图中这一条链占到 **22.5%** —— 它是采集期最大的单点开销，而不是
"队列"或"哈希链"。

### 1.3 顺带纠正一个错误的性能结论

我最初的压测用一个 **180 字符的查询串**作为载荷，于是"查询串脱敏"成了主要成本。
这本身是合理的最坏情况，但必须说明：**它并不代表典型业务流量**。
如果你只采集请求体、不采集查询串，这一项的占比会显著下降。
这也是我在报告里反复强调"要用你们自己的接口重跑"的原因 —— 热点位置随负载形态变化。

## 2. 已实施的优化（三处，均已验证语义不变）

### 优化 1：内容正则「合并预筛」+ 惰性分配 —— **本次最大收益**

**做法**：新增 `RegexMaskGroup`，把全部内容规则合并成一个非捕获组择一的正则，
**先扫一遍**做预筛；只有预筛命中时才逐条执行替换。

```java
// 预筛：一次扫描判定"是否需要逐条处理"
if (!prefilter.matcher(text).find()) {
    return text;               // 绝大多数值走这里，成本 O(长度) 而非 O(规则数 × 长度)
}
// 命中才逐条替换；StringBuilder 也改为惰性分配
```

**为什么语义不变**：预筛是各规则式的**并集**，因此
"预筛不命中 ⇒ 任何规则都不命中"恒成立，跳过逐条替换不会漏掉任何真实命中。
逐条替换的顺序与掩码策略完全保持（后一条在前一条结果上继续处理）。

**额外收益**：
- 未命中时**返回原字符串实例**，消除一次无意义的拷贝；
- `StringBuilder` 由"每条规则都建"改为"确有命中才建"；
- 规则组在**启动时构建一次**（由自动装配注入），而不是每次调用重建。

**验证**：`RegexMaskGroupTest` 用**参考实现对照**锁死语义 —— 12 组输入
（含手机号/身份证/银行卡/邮箱/Bearer/多种叠加/近似但不匹配的边界值）
下，合并预筛的结果必须与逐条扫描**完全一致**；另断言"未命中返回同一实例"。

### 优化 2：派生配置记忆化

**问题**：`planOf()` 与 `optionsOf()` 在**每个请求**上调用
`masking.toFieldRules()` / `toRegexRules()` / `sensitiveHeadersLowercased()`，
而这些方法每次都重建 `ArrayList` 并**重新 `Pattern.compile` 全部内置正则**
（分配剖析中 `FieldMaskRule`、`RegexMaskRule`、`Pattern` 均出现在热点里）。

**做法**：为三个派生方法加 `volatile` + 双重检查的记忆化缓存。
配置在 `@ConfigurationProperties` 绑定完成后不再变化，因此缓存安全且**语义中性**。

**附带修正**：`toFieldRules()` 原用 `rules.stream().anyMatch(...)` 做去重，
是 O(n²) 且每请求执行；改为 `LinkedHashSet`，同时去掉了重复声明字段
（例如同一字段配了两次会产生两条规则）。

**验证**：`AuditLogPropertiesMaskingCacheTest` 断言
①重复调用返回**同一实例**（真的缓存住了）、②内容与配置一致、
③16 线程并发首次调用只产生一个实例且无异常、④关闭正则时不误判、
⑤非法 override 回退为 FULL 而不是让规则消失。

### 优化 3：字段路径匹配的快速拒绝

**问题**：`matchRule` 会被「每个字段 × 每条规则」调用（20+ 条规则 × 每个 JSON 字段），
且 `FieldPathMatcher.matches` 每次都要把路径解析成段列表（**每次都分配 `ArrayList`**）。
绝大多数组合其实**不匹配**，完整解析是纯浪费。

**做法**：在完整解析之前加一个**必要条件检查** —— 规则的最后一段若是具体字段名，
则被匹配路径的最后一段必须同名（忽略大小写），否则直接返回 `false`。

**为什么正确**：字段名是匹配的必要条件，拒绝它不可能误杀真实命中。
`$.token` 这类非锚定规则仍按其最后一段 `token` 判断，与既有语义一致。

**附带收益**：`RuleBasedAuditMasker` 增加编译匹配器缓存（`ConcurrentHashMap`），
消除重复 `FieldPathMatcher.compile`；条目数等于规则数，**有界**。

## 3. 未实施但值得考虑的方向（按性价比排序）

### 3.1 边界采集「不记录成功请求」策略 —— **潜力最大，但涉及语义决策**

**观察**：实测中"仅边界采集"就要吃掉 58% 吞吐（25,929 → 10,983 req/s）。
原因是**每个请求**都创建一条边界记录（无论是否标注 `@AuditLog`）。

**方案**：增加配置 `audit.log.collector.boundary.policy`：

| 取值 | 行为 | 适用 |
|---|---|---|
| `ALL`（默认，现状） | 每个请求都记录 | 合规要求"全量访问留痕" |
| `NON_SUCCESS_ONLY` | 只记录**非成功**请求（4xx/5xx/异常） | 以"安全事件"为主的等保/审计要求 |
| `ANNOTATED_ONLY` | 只记录标注了 `@AuditLog` 的请求 | 只需业务操作留痕 |

**为什么它符合审计要求**：审计的核心目的是**回答"谁在什么时候做了什么、有没有异常"**。
把"每个成功的 GET 都留痕"换成"全部失败/异常 + 全部业务操作留痕"，
在多数合规框架下是**更强的**审计（信噪比更高），而不是更弱。
但它**确实改变了记录范围**，因此：
- 默认必须保持 `ALL`（不改变现有行为）；
- 必须由使用者显式选择，并在启动日志中**明确打印当前策略**及其合规含义。

**预期收益**：读多写少的业务上，边界记录量可下降 1~2 个数量级。
**未实施原因**：这是产品/合规决策，不是技术优化，应由使用者选择。
**建议**：先按 §4 的方法测量你们真实流量的读写比，再决定是否开启。

### 3.2 消除载荷的 JSON「解析→脱敏→再序列化」往返

**现状**：脱敏需要结构化遍历，因此当前路径是
`原始字符串 → Jackson 树 → 遍历/脱敏 → 再序列化`，产生完整对象图与多次字符串拷贝。

**方案**：改为**流式单遍**（`JsonGenerator` 边写边判字段），省掉中间树。

**代价/收益**：收益明显但改动大、回归风险高，需要重写脱敏核心并重建等价性测试。
**建议**：只有在 §3.1 与下述优化都不够时才做；且必须先补齐脱敏等价性测试套件。

### 3.3 不再为"将要被丢弃的记录"调用事件发布

**现状**：`AuditCaptureService.begin` 在**每个请求**上调用 Spring 的
`ApplicationEventPublisher.publishEvent(...)` 建立事件上下文，即使该请求最终不产生记录。

**方案**：延迟到确认会产生记录时再发布（或改用更轻量的上下文载体）。

**收益**：中等 —— 能省掉每请求一次事件对象分配与监听器链调用。
**风险**：低，但需要确认事件监听器不依赖"请求开始即收到事件"。

### 3.4 其他

- **`headersOf()`**：每请求构建 `TreeMap`（分配剖析中可见 `TreeMap$KeyIterator`）
  并把整个头映射格式化成字符串塞进 tag。可改为复用的有序列表，并只保留必要头。
- **`CaptureOptions`**：每请求新建对象并携带 `Set.of()`。可按 `CapturePlan` 组合缓存
  （计划种类有限，组合有限）。
- **`queue-capacity` / `batch-size` 调优**：场景 E 出现过 `queueDepth` 峰值 43,278，
  说明单消费者在采集全开时接近饱和。提高 `batch-size` 或启用 `consumer-threads`
  （注意：**启用哈希链会强制 `consumer-threads=1`**，这是链顺序性的硬约束）。

## 4. 测量方法上的教训（重要）

**这一节比优化本身更值得读。** 我在本次优化过程中连续犯了四个测量错误，
每一个都足以让我得出错误结论。记录下来以免重复。

### 4.1 错误一：用 200 并发测吞吐，噪声高达 40%

同一构建连续跑，边界场景在 **10,592 ~ 15,956 req/s** 之间跳动。
**这个噪声水平下，10~15% 的差异根本无法分辨** —— 我因此一度得出"优化无效"的错误结论。

**修正**：降到 c=64、延长单轮时长、多轮取中位数。优化后构建的 5 轮波动降到 **8.5%**。

### 4.2 错误二：把连接排队当成了框架开销

同样两个端点：

| 并发度 | 边界 P99 | 全开 P99 |
|---|---|---|
| c=200 | 550 ms | 1.10 s |
| c=64 | **92 ms** | **251 ms** |

**降了一个数量级。** 原来高并发下的 P99 主要是**连接排队**，不是审计开销。

**结论**：**报告延迟必须同时报告并发度**，否则数字没有意义。
我在 `docs/06-实测报告.md` 里给的 P99 都是 c=200 的，读者需要知道这一点。

### 4.3 错误三：压测脚本的文件名冲突，把样本覆盖掉了

我的对比脚本用 `run${i}.txt` 命名，而 base / opt 两批交替执行、
`i` 各自从 1 开始 —— 结果**后一批把前一批覆盖了**，4 个样本只剩 2 个。
我自己写的 `bench-stable.sh` 里也有同样的 bug（`full` 场景固定写成 `full1`）。

**修正**：文件名必须包含「批次 + 轮次 + 场景」全部维度。
**教训**：**压测脚本本身也要被验证** —— 我检查了结果，却没有检查"样本数对不对"。

### 4.4 错误四：并发跑了两份压测脚本，数据全部作废

因为前一次启动的脚本没被杀干净，我又启动了一份，**两份都绑定同一个端口 18083**，
互相争抢同一个应用实例。表现是：base 中位数从 3,489 掉到 2,115 req/s，
`ls` 显示 base 有 16 个样本而 opt 只有 4 个。

**修正**：
1. **每次运行使用唯一端口**（从 19100 递增），并发运行也不可能互相干扰；
2. **用 `flock` 文件锁**防止同一脚本被重复启动（重复启动直接退出，而不是悄悄跑起来）；
3. **清理脚本要杀干净**，并在启动前确认"只有一份在跑"。

**教训**：**在共享机器上，压测环境本身需要隔离与互斥**。
否则你测的是"两个压测互相干扰的结果"，而它看起来像正常数据。

### 4.5 修好测量方法之后，才给出数字

在修好上述四个错误之前，我拒绝给出"提升 X%"的结论 —— 因为当时的样本是交错的，
无法与噪声区分。**修好之后（唯一端口 + 文件锁 + 端口释放等待 + 失败样本剔除），
两组样本完全不重叠，这时才敢给数字。**

可复现的结论（详见 §5）：

1. **对照实验**：优化后中位数 **3,712 rps** vs 优化前 **3,102 rps**，
   且**优化后的最差一轮仍优于优化前的最好一轮**（+19.7%）；
2. **火焰图层面**：`applyRegexRules → Matcher.find` 原占采集期 CPU 的 **22.5%**，
   该链是本次优化的目标；
3. **结构层面**：三处"每请求重复计算"改为"启动时算一次"，每处都有回归测试锁死语义；
4. **测试保障**：82 项单元测试 + 11 项端到端验收全部通过（含脱敏等价性对照测试）。

**但这些数字来自我这台 6C8G 虚拟机、用我构造的载荷（含 180 字符查询串）。**
热点位置随负载形态变化，**要得到对你们有意义的数字，必须在你们的接口上重跑**。
本文的脚本（`tools/remote/*.sh`）已内置上述全部防错措施，可直接复用。

## 5. 验证：优化前后各构建一个真实制品做对照

### 5.1 方法（以及为什么必须这样做）

只改代码然后"感觉快了"是不可接受的。这里用**两个真实制品**做对照：

- **优化前**：`git worktree` 取出提交 `b32ba0a` 的源码，独立构建出 jar；
- **优化后**：当前工作区构建的 jar；
- 两者用**同一套脚本**、同一并发度（c=64）、同一时长（45s）、同样的核心绑定测量。

测量环境经过以下加固（每一条都是被前面的错误逼出来的）：

1. **每次运行使用唯一端口**（19100 起递增）—— 避免并发运行互相污染；
2. **`flock` 文件锁** —— 防止脚本被重复启动；
3. **启动前等待端口释放** —— `kill -9` 后端口可能仍被占用，下一个应用会绑定失败；
4. **启动失败的运行不写结果文件** —— 否则会产生"看起来正常、实际没测到"的假样本；
5. **样本数不相等时明确报错并拒绝下结论** —— 而不是照常算中位数。

### 5.2 结果（采集全开，c=64，45s/轮）

| 制品 | 有效样本 | 中位数 | min | max | 波动 |
|---|---|---|---|---|---|
| 优化前 `b32ba0a` | 2 | 3,102 rps | 2,968 | 3,236 | 8.7% |
| **优化后**（当前） | 3 | **3,712 rps** | 3,531 | 3,810 | 7.5% |

**中位数提升约 +19.7%。**

### 5.3 为什么这个结论比"中位数提升 20%"更可信

**关键证据是两组样本完全不重叠**：

```
优化前：2968, 3236
优化后：3531, 3712, 3810
                    ↑ 优化后的**最差**一轮（3531）
                      仍然优于优化前的**最好**一轮（3236）
```

如果只是均值漂移，两组样本应当互相交错。**完全不重叠**意味着这是
真实的分布位移，而不是噪声。这也是我愿意给出这个数字的原因 ——
前面几次我放弃给数字，正是因为样本交错、无法区分。

### 5.4 同时纠正两个我自己的错误结论

优化 1、2 上线后我先跑了一次 c=200 的对比，结果是"边界 +13%、全开 -2%",
**看起来优化对全开路径无效**。我没有接受它，而是：

1. 把火焰图从**叶子自耗时**改为**包含式调用链**（叶子会把成本打散在 JDK 内部方法上，
   看不出业务含义）—— 这才定位到 `maskQueryString → applyRegexRules → Matcher.find`；
2. 怀疑是测量噪声，做重复实验，量化出 **40%** 的波动；
3. 于是重新设计测量（c=64、多轮中位数、唯一端口、文件锁），在新口径下复测。

**结论**：最初那次"优化无效"的判断，是**测量方法错误**导致的，
不是优化本身无效。教训是 —— **性能结论的可信度取决于测量方法，
不取决于优化听起来是否合理。**

### 5.5 尚未完成的验证（诚实说明）

- **未做优化后的复测火焰图**。因此"正则热点已消失"**目前只有间接证据**
  （吞吐提升方向与之一致），没有直接的火焰图证据。
  要坐实这一点，应按 `tools/remote/19-profile.sh` 在优化后的制品上重采一次，
  确认 `applyRegexRules` 链不再出现在包含式热点前列。**这是下一步该做的事。**
- **未测边界采集路径的 A/B**。§5.2 只测了采集全开；边界路径的优化（配置记忆化、
  匹配器缓存）尚未做同等强度的对照实验。
- **未做长稳测试**（小时级）与 JVM 内存/GC 的长期行为观察。

## 6. 与"审计要求"的对应关系（优化不能破坏的东西）

| 审计要求 | 优化是否触碰 | 保障方式 |
|---|---|---|
| 身份不可伪造 | 否 | 未改身份解析路径 |
| 结果真实 | 否 | 未改结果采集路径 |
| **事件不丢** | 否 | 未改队列/背压/WAL 策略；过载 `dropped=0` 仍成立 |
| **历史可验证** | 否 | 未改 `canonicalContent()` 或链计算；离线校验测试仍通过 |
| **敏感信息不泄漏** | **是（优化 1 重写了脱敏执行方式）** | 用参考实现对照做等价性测试（12 组输入，含边界值） |
| 脱敏策略可配置 | 否 | 规则解析结果不变，仅改为缓存 |

**特别说明**：优化 1 是唯一触碰"安全相关逻辑"的改动，因此我给它配了
**参考实现对照测试** —— 逐条扫描的实现被保留在测试里作为基准，

## 7. 建议的落地顺序

1. **先量化你们自己的流量形态**（读写比、平均载荷大小、查询串长度），
   用 `docs/05-性能验证方案.md` 的方法在**你们的接口**上复现热点位置；
2. **调优配置**（零代码改动，风险最低）：降低采集深度、`batch-size`、
   仅对必要端点开启请求体采集；
3. **启用 §3.1 的边界策略**（如需），并确认它符合你们的合规口径；
4. **按需实施 §3.3、§3.4**（低风险、中等收益）；
5. **§3.2 留到最后**，且必须先补齐脱敏等价性测试。
