# audit-log 架构评审报告

评审对象：`audit-log`（原单模块技术原型）+ 其 CSDN 设计文章
评审视角：框架 / 平台架构（不含业务代码风格）
评审方式：源码逐文件走查 + 本地编译验证（`mvn compile` 通过，JDK 17 / Spring Boot 3.5.8）

---

## 结论

技术切入点是**正确的**：用 Spring MVC 内层扩展点做采集、注解驱动、事件解耦，方向比 AOP 更靠内。
但被评审的实现，成熟度是**「技术演示（Demo）」**，不具备企业级审计框架的必备属性。

**最关键的缺陷全部不在性能上，而在审计的存在理由上：**

| 不变量 | 要求 | 原实现 |
|---|---|---|
| 身份不可伪造 | 主体只能来自认证上下文 | ❌ 取自客户端可控制的请求头 `userId` |
| 结果真实 | 与事务提交边界对齐、如实记录成败 | ❌ `finally` 内同步发布，回滚也记；状态码靠猜 |
| 事件不丢 | 有界队列 + 明确背压 + 持久化 | ❌ 无持久化、可静默丢弃、可静默失效 |
| 历史不可篡改 | append-only + 哈希链/签名 + 独立存储 | ❌ 仅 `log.info`，无任何防篡改与保留策略 |

而文章 70% 的篇幅论证的「高性能」，其唯一证据（18,152 QPS）取自一个**把所有采集开关都关掉的端点**，因此该结论不成立。

## 一、致命级（P0）

### F1 基准测试的端点关闭了全部采集 → 核心性能结论无效

```java
@AuditLog(name = "查询用户信息3", logHeaders = false, logRequestParams = false, logResponseParams = false)
@GetMapping("/queryUserInfo3")
```

压测只执行了 `map.containsKey()` + `new AuditLogEvent()` + `publishEvent()`，采集逻辑（header 脱敏遍历、参数序列化、响应序列化）一行未执行。且无 AOP 对照、无单机 GC/CPU/P99 数据。
→ 「选择 Spring MVC 扩展机制而非 AOP 的正确性」缺少证据链。

### F2 审计与业务事务不一致：回滚的操作被记成成功

事件在 `finally` 中、方法执行后同步发布（`AuditLogServletInvocableHandlerMethod:65-86`）。Controller 位于事务提交之前，因此：

- 业务回滚 → 审计记录照样产生，且 `responseCode = 200`；
- 审计「成功」无法证明数据变更已提交。

这是审计最严重的一类错误：**记录了没有发生的事（假阳性），且事后无法识别**。

### F3 结果字段是猜的

```java
String exceptionInfo = exception != null ? exception.getMessage() : "";
int responseCode = exception != null ? 500 : 200;
```

读真实响应的那行代码被注释掉；不处理 `@ResponseStatus`、全局 `@ExceptionHandler`、HTTP 200 + 业务错误码；丢失异常类型与根因；只 catch `Exception`；`responseParams` 是 `toString()` 而非报文。
→ 事后**无法区分"操作成功"与"被拒绝"**。

### F4 身份可伪造 + 主键硬编码（安全红线）

```java
String userId = request.getHeader("userId");          // 客户端完全可控
new AuditLogDO(121212L, userId, ...)                  // 所有记录同一主键
```

- 任意请求可伪造成他人行为 → **不可否认性归零**，并引入审计日志注入；
- 无全局唯一事件 ID → 无法去重、定位、做哈希链；
- 无 `traceId`、无租户维度 → 微服务因果链无法重建、多租户无法隔离。

### F5 采集面只覆盖方法调用层 → 最重要的安全事件全部漏采

挂载在 `doInvoke`，只有进入方法体才采集。因此认证失败、401/403、限流熔断、参数绑定失败、404、静态资源、非 MVC 入口（MQ/定时任务/gRPC）**一件都记不到**。
同时 `WebMvcRegistrations` 只存在于 Servlet MVC → 一旦业务改用 WebFlux 框架整体失效，而文章标题未加限定。

## 二、高危级（P1）

### H1 静默失效：看起来在跑，实际什么都没记

启动期自制扫描器构建 `Map<Method, BO>`（`AuditLogConfiguration:83-135`），存在四个失配点，且**全部降级为「静默放过」**：

1. `ClassUtils.forName` 在 BeanDefinition 注册阶段提前加载所有类 → 可选依赖缺失会 `NoClassDefFoundError` 直接让应用**启动失败**；扫描异常被 `logger.error` 吞掉；
2. `getDeclaredMethods()` + `isAnnotationPresent` → **不识别继承/接口上的注解**；
3. 用 `Method` 作跨生命周期 key → 不同 ClassLoader、代理形态下 `equals` 失效；
4. 控制器被 CGLIB 增强时，注解可能读不到。

审计最不能接受的失败模式就是静默降级，必须**大声失败**（启动校验 + 运行期计数 + 健康检查）。

### H2 「零性能损耗」不成立：发布是请求线程内同步调用

异步与否取决于应用是否加了 `@EnableAsync`（写在示例启动类上，不是框架提供）。应用忘记加 → `@Async` 失效 → **监听器在请求线程内同步执行**，宣传的异步不存在且无任何检测。
`AsyncConfig` 整个文件被注释 → 框架没有自己的执行器，与他人的 `@Async` 争抢线程；注释里的 `CallerRunsPolicy` 会把落库开销压回请求线程（压缩 SLA），与「不应丢弃任务」自相矛盾。

### H3 完整性（不丢 / 可审计）在实现里为零

落点是 `log.info`（与应用日志混存，会滚动删除）；无 DB/MQ/本地 WAL；无重试、无幂等、无死信；停机丢队列；无防篡改（哈希链/签名/WORM）；无保留期与归档（只增不减终将打满磁盘）；无访问控制与「审计的审计」。

### H4 采集方式导致「日志不可解析」+「敏感数据泄漏」

- `Stream.of(args).map(Object::toString)` / `returnValue.toString()` → 非结构化、不可逆、无法索引、无法喂 SIEM；浅层 toString 丢失嵌套语义；框架参数（`HttpServletRequest`/`Principal`/`Model`/`BindingResult`/`MultipartFile`）全被灌入；
- 异步线程内再遍历对象图 → JPA 懒加载触发 `LazyInitializationException` 或额外 SQL；
- 脱敏两处独立缺陷：
  1. **大小写敏感** `sensitiveHeaders.contains(headerName)`，默认黑名单是小写 `authorization`/`token`，而实际 header 是 `Authorization`/`X-Auth-Token`/`Cookie` → **真实令牌原样入库**；
  2. **只管 header 名，完全不管报文体** → body 里的 `password`/`idCard`/`bankCard`/手机号原样入库。
  3. 仅按字段名匹配，无递归 JSON 路径、无正则、无「未知即脱敏」的保守默认。

### H5 数据模型缺少审计语义

`AuditLogDO` 13 个平铺字段，缺失：事件唯一 ID、接收时间/时区、租户/会话/认证方式、动作类型枚举、资源与资源 ID、真实结果、`traceId`、变更前后快照、完整性与存储元数据。
→ 这是**操作流水（access log）模型**，不是**审计（audit trail）模型**。

### H6 异步上下文不传播

`@Async` 切换线程后，`RequestContextHolder` / `SecurityContext`(THREADLOCAL) / MDC 全部不继承，且框架未提供 `TaskDecorator`。→ 监听器里拿不到请求上下文与链路 ID，H2 建议的链路关联无法落地。

## 三、中危级（P2，框架工程化）

- **M1 全局替换 `RequestMappingHandlerAdapter`**：`WebMvcRegistrations` 全局仅一份生效，与宿主/其他组件**互斥且不可预期**；依赖 `createInvocableHandlerMethod`/`doInvoke` 等 protected 内部方法，跨 Spring 版本随时变动，且未声明版本兼容范围。
- **M2「禁用/缺失」即启动失败**：`auditLogMethods` bean 仅在 `enable=true` 注册，而消费者构造时无条件 `context.getBean("auditLogMethods")` + 强制转型 → 禁用功能反而抛异常。字符串 bean 名 + 硬编码类型作为内部契约，是典型脆弱耦合。
- **M3 无配置模型、无 SPI**：全仓库 grep `ConfigurationProperties|Environment|@Value` **零命中**。无全局开关/采样/截断/大小上限/可信任代理头/批量/刷盘/重试配置；存储策略硬编码在 `@Component` 监听器里，文章宣称的「易于扩展」没有任何接口承载；该 `@Component` 在外部 jar 场景下若不在组件扫描路径内则**根本不会被注册** → 事件无人消费、审计静默全丢。
- **M4 注解 / README / 代码三方不一致**：README 里的 `basePackages`、`logHeaders`、`logRequest`、`logResponse`、`sensitiveHeaders`、`${audit.log.enable:true}` 占位符、`@Log`、`AuditLogConfig`、`MethodLog`、`AuditLogHandlerAdapter`、`AuditLogHandlerMethod`、`AuditLogRequestEvent`、`AuditLogTest`、`AuditLogIntegrationTest` **全部不存在**；README 说 DEBUG 而代码是 `log.info`；唯一测试 `Test1.contextLoads` 仅打印一个 map、无断言。
- **M5 交付物不是「框架」**：单模块混装框架与示例；`pom.xml` 无 license/developers/scm/distributionManagement，版本 `1.0-SNAPSHOT`；Gitee 仓库**未声明 LICENSE**（无授权即无法在企业内引入）；无自动配置、无 starter、无版本兼容矩阵与变更日志。
- **M6 其他**：`finally` 中无异常隔离，采集/序列化异常会**覆盖原始业务异常**；`doInvoke` 之上还有流式/响应式处理，`Mono`/`Flux`/`SseEmitter` 的耗时与响应语义失真；日志内容未做输出编码，存在存储型 XSS / 日志伪造风险。

## 四、架构层面的根因

1. **没有 ADR**：为什么用 HandlerAdapter 而非 Filter/Interceptor/`@TransactionalEventListener`，代价是什么，未记录。实际权衡是：相比 AOP 只省下纳秒级的代理开销，却付出「丢失响应式、丢失非 MVC 入口、强耦合 Spring 内部方法、与其他 `WebMvcRegistrations` 互斥」的代价；而「精确匹配」的收益来自注解短路，AOP/Interceptor 同样可以做到。**收益与代价严重不匹配。**
2. **没有定义审计不变量**（见上表），导致实现处处模糊。
3. **没有失败语义决策**：采集失败/队列满/存储不可用时业务是否继续，完全未设计。
4. **没有数据生命周期**：保留期、归档、冷热分层、查询权限、租户隔离。
5. **优化了次要矛盾**：真实瓶颈是序列化 + 脱敏 + 落盘，而非「在不在 AOP」。

## 五、原有资产中值得保留的部分

- 用 Spring MVC 内层扩展点 + 注解驱动 + 事件解耦的整体思路；
- `@EnableAuditLog` 作为统一开关的入口设计；
- 方法级三开关（headers/request/response）与敏感字段声明的**配置粒度**设计；
- 事件驱动、采集与处置分离的分层意识。

整改方案（见 `docs/02-整改方案.md`）以这些为基础重建，而非推翻重写。
