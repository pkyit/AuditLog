# 10 - 外部评审问题的修复记录

**背景**：外部评审报告（GLM，见 `docs/09-外部评审复核.md`）列出 1 致命 + 4 高 + 5 中 + 8 低共 18 项问题。
本文件记录**每一项的处置**：已修复、部分修复、或有意不做（附理由）。

**原则**：不为了"看起来全都改了"而做表面修改。
凡是**不修反而更安全**的，明确说明理由；凡是行为变更，都配回归测试。

---

## 一、P0：发布阻断

### C1 大请求体被截断，破坏宿主业务 —— ✅ 已修复

`CachedBodyHttpServletRequest` 从"先读进内存再让业务读副本"改为 **tee（透传 + 旁路缓存）**。

- 业务永远读到完整报文（实测 1,000,000 字节完整到达，修复前为 65,536）；
- 审计保留前 `max-cache-bytes` 字节并标记 `truncated=true`；
- 内存占用仍有上限，不会因大文件上传 OOM。

回归测试 `CachedBodyHttpServletRequestTest`（9 例）锁死该行为。
**该测试在编写过程中真的抓到了我自己引入的回归**（复用同一个 `ByteArrayInputStream`
导致第二次读为 0 字节），已改为每次返回新流。

## 二、P0.5：审计正确性根基

### C2 链 head 不持久化，重启/崩溃后链永久断裂 —— ✅ 已修复

这是本次改动最大的一项，分四个部分：

1. **新增 `ChainState` + `AuditChainStore` SPI**
   持久化链头与 `lastDeliveredSeq`；`FileChainStateStore` 用"临时文件 + 原子改名"写入，
   保证读到的永远是完整状态（不会读到半个文件）。

2. **启动时恢复链状态**（`AuditPipeline.restoreChainState()`，在 `replay()` **之前**调用）
   顺序至关重要：先恢复再重放，否则重放会以 GENESIS 重新链接，把链头推进到错误的哈希上。

3. **重放不重复链接**（`linkForDelivery`）
   已有 `recordHash` 的记录**原样透传**，并把链头对齐到它 ——
   避免"对已链接记录再 link 一次"导致内存链头与存储内容永久不一致。

4. **存储幂等**（`JdbcAuditStore`）
   区分「主键重复」与「真实故障」：重复视为成功（WAL 重放的正常情形），
   真实故障才抛出交给重试/WAL/死信。此前一律当故障，会导致**重放已落库的记录时整批进死信**。
   同时新增 `AuditStore.recoverChainState()`：状态文件丢失时从存储回读链尾兜底，
   让恢复能力不依赖单一文件。

**实测验证**（真实服务器、真实文件存储、两次启动）：

```
第一次运行: head=5af5dfc0... seq=5        <- 链状态已原子落盘
第二次启动: seq 从 6 继续（不再从 1 重来）
落盘 8 条记录: seq 范围 1..8，无重复
HMAC 重算 = 存储值 (MATCH)；signature 重算 = 存储值 (MATCH)
结论: 跨重启链连续、可离线校验
```

回归测试 `ChainPersistenceTest`（5 例）：跨重启链连续、seq 不回退、
状态文件丢失时从存储兜底恢复、冷启动从 GENESIS、状态文件写入原子性。

## 三、P1：高优先级

### H1 异步请求未被覆盖 —— ✅ 已修复

`shouldNotFilterAsyncDispatch()` 改为返回 `false`（处理 ASYNC dispatch），
并在初始 dispatch 结束时**判断 `isAsyncStarted()`**：

- 同步：立即收尾发布（原行为）；
- 异步：把上下文暂存到请求属性，等 ASYNC dispatch 回来再收尾 ——
  避免在 `startAsync()` 时刻就记下"占位 200 + 假耗时"的错误记录；
- 同时注册 `AsyncListener` 兜底：超时/出错/容器直接完成时也保证有收尾点，
  **否则这条审计记录会彻底丢失**（丢记录比记录不准更不可接受）。

### H2 `masking.enabled=false` 无效且日志说谎 —— ✅ 已修复

改为**让配置真实生效**：`RuleBasedAuditMasker` 增加 `customMaskingEnabled`，
为 `false` 时载荷与查询串原样返回；日志文案改为与行为一致。

**同时保留安全底线**：`Authorization` / `Cookie` / `X-API-Key` 等凭据类请求头
**始终**被打码，不受该开关影响。理由：一个配置失误不该能把令牌写进审计库 ——
那比"配置不生效"严重得多。这一点在属性 javadoc 与启动告警中都写明了。

### H3 `@EnableAuditLog` 属性静默无效（死代码）—— ✅ 已修复

新增 `AuditLogAnnotationRegistrar`（`ImportBeanDefinitionRegistrar`），
把注解属性注册为 **`AuditLogAnnotationProperties` Bean**，由启动校验真实消费：

- `methodCollector`：与 `collector.method.enabled` 共同决定是否采集（注解不再被忽略）；
- `basePackages` / `defaultActionType`：在启动日志中如实打印，并**校验声明范围与实际采集范围是否一致**，
  不一致则明确告警。

**为什么不直接按包过滤**：方法级元数据来自 Spring 真实的 `HandlerMapping`，
按注解包名过滤会**静默丢弃**包外的 `@AuditLog` 方法 —— 那比"范围没生效"更糟。
因此选择"如实暴露差异"而不是"静默缩小范围"。
`exclude()` 与 `enable=false` 分支同样不再丢弃属性。

### H4 类级 `@AuditLog` 不生效 —— ✅ 已修复

`AuditMethodRegistry` 新增 `resolveAnnotation()`：**先查方法级，未命中再查声明类**，
合并语义为"方法级覆盖类级"。

事实依据用测试固化了（`ClassLevelAuditLogVisibilityTest`）：
Spring 的 `AnnotatedElementUtils.findMergedAnnotation(Method, ...)`
**看不到**仅声明在类上的注解，因此必须显式回退 ——
否则 `@Target(TYPE)`、`@Inherited` 与 `ignore()` 的 javadoc 都是无法兑现的承诺。

## 四、P2：中优先级

### M1 热路径上 O(WAL 行数) 磁盘 I/O —— ✅ 已修复

`FileAuditJournal.pendingCount()` 原本遍历**所有** WAL 分段做 `Files.lines().count()`，
而它处在采集热路径上（每次成功入队都会调用 `updateDepthGauge()`）。

改为内存计数器 `onDiskLines`：只在三处更新 —— 启动扫描一次、写线程追加、保留策略删除分段。
`pendingCount()` 变成**纯内存读，零 I/O**。

> 这条与 `docs/07` 的性能结论直接相关：我的压测**从未触发过 spill**，
> 所以"采集全开约为基线 11%"没有覆盖"已发生 spill 之后的稳态"。

### M2 背压路径指标账目错误 —— ✅ 已修复

两个问题分别处理：

1. **`dropOldestAndOffer` 非原子**：原实现 `poll()` 后 `offer()`，
   并发下 offer 可能失败 → 新元素被静默丢弃却仍计 ENQUEUED。
   改为循环重试，并返回 `DropOutcome{accepted, discarded}` 精确报告结果：
   **只要丢弃过元素就一定把新元素放进去**；确实无法入队时如实返回失败，由调用方计入丢弃。
2. **`BACKPRESSURE` 无条件递增**：原实现把"尝试次数"记成了"背压事件"。
   改为**只在队列真的满时**递增（每个策略各自在失败分支递增）。

### M3 哈希链未覆盖归属字段 —— ✅ 已修复（schemaVersion = 2）

`canonicalContent()` 纳入：`principalName` / `sessionId` / `authType` / `clientIp` /
`userAgent` / `queryString` / `serviceName` / `instanceId` / `error.message` / `tags`。

**版本兼容是关键**：摘要**按记录自带的 `schemaVersion` 选择格式** ——
v1 记录仍用 v1 规则重算，因此**升级不会让历史链校验失败**（否则格式演进无法落地）。
`tags` 按 key 排序后拼接，保证跨 JVM 确定性。

端到端验收 `A7 防篡改哈希链` 在 v2 下仍通过（完好链校验通过、篡改后定位到 seq=6）。

### M4 注册表按裸方法名回退 → 元数据错配 —— ✅ 已修复

回退匹配**约束在同一个声明类内**（含继承关系）。
此前按裸方法名跨控制器回退，在 `getById`/`list`/`save` 这类同名方法上
会让"未标注的 B 控制器方法"命中"已标注的 A 控制器元数据"，
审计记录带上错误的操作名与 resourceType —— **错配比缺失危害更大**。

### M5 order=-100 与 Spring Security 相同 —— ✅ 已修复

默认 `order` 改为 **-150**（严格小于 Security 的 -100），
并在 javadoc 中说明"同 order 值不保证先后"，以及认证失败事件漏采的后果。

## 五、P3：低优先级

| 项 | 处置 | 说明 |
|---|---|---|
| **L1** 异常透传时 `httpStatus=200 + outcome=FAILURE` | ✅ 已修复 | 异常透传且状态码仍是 2xx 时把 `httpStatus` **置空**（未知）+ 加 tag 说明。宁可"未知"也不要"错误" |
| **L2** 文件字节数按 char 计数 | ✅ 已修复 | `JsonFileAuditStore` 与 `FileAuditJournal` 均改为 UTF-8 字节数；中文内容下轮转阈值不再偏小 |
| **L3** 静态资源 exclude 模式不匹配子目录 | ✅ 已修复 | 默认值由 `*.css` 改为 `/**/*.css`（Ant 的 `*` 不跨目录分隔符） |
| **L4** checkpoint 每批 truncate 重写 | ⚠️ **有意不修** | 见下方说明 |
| **L5** 停机时链序可能交错 | ✅ 已修复 | 消费者未在 10s 内退出时**明确告警**（暴露风险而非掩盖）；`parkNanos` 不可中断是有意设计（防止丢数据），不能为了停机速度牺牲它 |
| **L6** `submit(record, noQueue)` 参数无调用方 | ⚠️ **有意保留** | 它是 public API 的一部分（文档说明用于停机阶段最终刷新），且 `submit(record)` 内部调用它。删除会破坏 API 兼容性，收益仅为"少一个参数" |
| **L7** `captureResponseBody=true` 仍只输出摘要 | ✅ 已修复 | 开启时**启动告警**明确说明"拿不到响应正文，开关不会改变实际采集内容"，不再给出误导性暗示 |
| **L8** `enable=false` 时属性被丢弃 | ✅ 已修复 | 随 H3 一并处理（`AuditLogAnnotationRegistrar` 在 `enable=false` 时不注册，与"不启用"语义一致） |

### L4 为什么不修（这是有意的技术判断）

L4 建议把 checkpoint 的每批重写改为"按 seq 阈值节流"。

我**没有**这样做，理由有两条：

1. **它不在采集路径上**。checkpoint 由消费者线程在投递成功后调用，写的是几字节的小文件，
   对请求延迟没有直接影响 —— 与 M1（在采集热路径上做全量扫描）性质完全不同。
2. **节流会放大崩溃时的重复投递窗口**。checkpoint 记录"已成功投递到哪个 seq"，
   节流意味着崩溃后这个值可能偏旧，于是重启时会重放**已经落库**的记录。
   虽然存储幂等（C2 已修）能让重放安全，但代价是"用正确性余量换一个不在热路径上的微小收益"——
   这笔交易不划算。

**结论**：保持现状，并把理由记录在此，避免下一个人重复提出。

## 七、仍存在的已知局限（如实声明）

1. **响应正文不采集**：`captureResponseBody` 只影响是否记录摘要，拿不到正文。
   现在会在启动时告警说明，但功能本身**未实现**。
2. **异步场景的端到端覆盖有限**：H1 实现了 ASYNC dispatch 收尾与超时/错误兜底，
   但**没有为异步路径编写自动化测试**（缺少合适的测试容器与异步控制器样例），
   目前只做了代码级正确性论证。这是下一步该补的。
3. **哈希链与多消费者互斥**：`consumer-threads>1` 会破坏链序，框架已强制降为 1 并告警。
4. **性能结论的适用边界**：`docs/07` 的对照实验只覆盖了"未触发 spill"的稳态；
   spill 之后（M1 已修）的行为需要重新压测确认。
