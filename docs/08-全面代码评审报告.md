## 三、缺陷清单

严重度定义：**C（Critical）** 破坏宿主业务或审计正确性根基；**H（High）** 宣称的能力实际无效或产生错误数据；**M（Medium）** 特定条件下性能/指标/语义受损；**L（Low）** 打磨项。

### C1【致命】大请求体被截断，业务侧收到的报文不完整

- **位置**：`CachedBodyHttpServletRequest.wrap()`（42-62 行）+ `getInputStream()`（76-105 行）；入口 `AuditLogServletFilter.doFilterInternal`（90-93 行）
- **根因**：`wrap()` 从真实输入流最多读 `maxCachedBodyBytes`（默认 **64KB**）后停止，未消费剩余字节；包装器的 `getInputStream()`/`getReader()` 只返回已缓存字节。下游业务（`@RequestBody` 等）读到的是**被截断的报文**。
- **触发条件**：任何 POST/PUT/PATCH/DELETE 且请求体 > 64KB（`hasBody()` 仅判断长度非 0，无"超限则不包装"的旁路）。
- **影响**：启用审计（默认配置）后，大 JSON 提交直接解析失败或**静默丢数据**。这不是审计自身的缺陷，是**审计框架破坏了宿主业务的功能正确性**，属于发布阻断项。
- **修复方向**（二选一）：
  1. 改用 Spring `ContentCachingRequestWrapper` 的"随读随拷"模式：业务读完整流，审计侧拿到"业务已读的前 N 字节"，超限部分审计截断、业务不受影响；
  2. 若坚持入口缓存：`Content-Length` 超过 `maxCachedBodyBytes` 时**不包装**（放弃该请求的正文采集，只记元信息），绝不部分消费。
- **回归用例**：POST 1MB JSON，断言业务侧收到的对象完整 + 审计载荷带 truncated 标记。

### C2【高】哈希链 head 不持久化，崩溃恢复路径使链永久断裂

- **位置**：`Sha256AuditChain`（22 行 `private String head = GENESIS`）、`HmacAuditChain`（23 行）；`AuditPipeline.deliver()`（339-361 行）；`FileAuditJournal.checkpoint()`
- **两个失效模式**：
  1. **正常重启**：head 从 GENESIS 重新起链。新记录的 `prevHash` 与存储中上一条记录的 `recordHash` 无法衔接——任何跨重启的外部全链校验必然在重启边界报"篡改"。
  2. **崩溃恢复（更糟）**：在 `store.save(batch)` 成功之后、`journal.checkpoint()` 之前崩溃 → 重启后 WAL 重放这批记录 → 链以新 head 重新链接它们 → `JdbcAuditStore` 按主键幂等拒绝（batchUpdate 整批失败）→ **整批进死信**（含新增记录），且内存 head 前进到了"从未落库的哈希"上 → 此后所有 live 记录的 `prevHash` 指向存储中不存在的值。外部校验永久失效，且无任何指标暴露这一状态。
- **附带问题**：`actuator` 的链校验只验内存 `recentRecords`，以上两种断裂它都发现不了——给出"链完好"的假信号。
- **修复方向**：启动时从存储 tail 读取最后一条 `(seq, record_hash)` 恢复 head 与 seq 基准；或每批投递后将 `(head, lastDeliveredSeq)` 与 checkpoint 一起原子落盘；重放遇存储幂等拒绝时，不应把"已存在"当失败（JDBC 侧需区分 duplicate-key 与真实故障，前者视为成功）。actuator 链校验增加"从存储读回校验"入口。

### H1【高】Spring MVC 异步请求未被覆盖，且未声明为已知局限

- **位置**：`AuditLogServletFilter`（`OncePerRequestFilter` 默认跳过 ASYNC dispatch）；`AuditRequestContextHolder`（基于 request attributes）
- **表现**：`Callable`/`DeferredResult`/`WebAsyncTask`/`StreamingResponseBody`/SSE 场景下，`startAsync()` 后初始线程立即返回，过滤器的 `finally` **提前发布**记录：状态码是占位 200、耗时只算到 startAsync、事务结果可能尚未写回。ASYNC dispatch 二次进入时被 OncePerRequestFilter 跳过，不会修正。
- **影响**：所有异步接口产生**系统性错误**的审计记录（假成功/假耗时），恰是 README"已知局限"一节没有列出的那一类。
- **修复方向**：覆盖 `shouldNotFilterAsyncDispatch()` 返回 false + 在 `AsyncListener.onComplete/onError/onTimeout` 中触发真正的 `finish`；短期兜底是在已知局限中如实声明。

### H2【高】`audit.log.masking.enabled=false` 配置完全无效，且日志输出相反的承诺

- **位置**：`AuditLogAutoConfiguration.auditMasker()`（124-134 行）
- **事实**：`masking.isEnabled()` 全仓库仅此一处消费，且只用于打印警告："请求载荷将按原文记录"。`RuleBasedAuditMasker` 内部没有任何 enabled 分支；`AuditCaptureService` 采集路径无条件调用脱敏。
- **影响**：配置了 `masking.enabled=false` 的用户以为关闭了脱敏（例如内网系统想保留原文便于排查），实际数据仍被脱敏——**配置静默无效**，这正是本框架自己宣称要消灭的失败模式；同时启动日志明确说了谎。
- **修复方向**：要么让配置真实生效（透传到 CaptureOptions，脱敏器短路），要么删除该配置项并改警告文案为"脱敏为强制行为，不可关闭"（合规上后者更合理——那就删配置，别留一个骗人的开关）。

### H3【高】`@EnableAuditLog` 的属性大部分静默无效（含死代码）

- **位置**：`AuditLogImportSelector`（47-51 行）、`AuditLogAnnotationProperties`
- **事实**：
  - `new AuditLogAnnotationProperties(...)` 的结果**未注册为 Bean、未被任何代码读取**——纯死代码；
  - `scanBasePackages`：宣称"缩小扫描范围"，实际元数据来源是全量 `RequestMappingHandlerMapping`，包参数被丢弃，**无任何限制效果**；
  - `methodCollector=false`：宣称"等价于 collector.method.enabled"，实际什么也不做；
  - `defaultActionType`：同样被丢弃（生效的是 properties 里的同名配置）。
- **影响**：注解属性是使用者的显式意图表达，静默忽略 = 注解层面的"静默失效"。
- **修复方向**：把注解属性桥接到 `AuditLogAnnotationProperties` Bean 并在装配/校验时消费；或删掉不打算支持的属性，让编译期就不存在虚假承诺。

### H4【高】类级 `@AuditLog` 声明支持（`@Target(TYPE)` + `@Inherited`），注册表只扫方法级

- **位置**：`AuditLog` 注解（`@Target({METHOD, TYPE})`；`ignore()` 的 javadoc 明言"用于在类级别开启后单独排除某方法"）；`AuditMethodRegistry.populate`（80 行）只做 `AnnotatedElementUtils.findMergedAnnotation(method, ...)`——该调用**不会向上查声明类的注解**。
- **影响**：控制器类上标 `@AuditLog` 的用户以为全类生效，实际一个方法都不采（好在会走边界通道兜底，不至于漏事件，但语义字段全丢且无告警）。
- **修复方向**：`populate` 中先查方法级，未命中再查 `handlerMethod.getBeanType()` 的类级注解（合并语义：方法级覆盖类级）。

### M1【中】`pendingCount()` 在采集热路径上做 O(WAL 行数) 磁盘 I/O

- **位置**：`AuditPipeline.updateDepthGauge()`（每次成功入队调用）→ `FileAuditJournal.pendingCount()`（201-219 行，`Files.lines().count()` 遍历**所有** WAL 分段）
- **影响**：一旦发生过 spill（分段文件在重放+保留清理之前一直存在），**每个请求的入队都付出全量 WAL 行扫描的 I/O**。这与"提交路径只做三件轻量的事、不做任何 I/O"的类注释直接矛盾，打在框架核心卖点上。
- **修复方向**：`FileAuditJournal` 内部维护 `onDiskLines` 计数器（写线程更新、checkpoint 时扣减），`pendingCount()` 变纯内存读；精确遍历只留给健康检查。

### M2【中】背压路径的指标账目错误

- **位置**：
  - `BoundedRingQueue.dropOldestAndOffer()`（97-103 行）：`poll()` 与 `offer()` 非原子。并发生产者竞争下新记录可能 offer 失败被**静默丢失**，而 `AuditPipeline.offerDropOldest`（236-248 行）在 `discarded == null` 分支照样计 `ENQUEUED` 并返回 true——丢了数据却记了成功入账。
  - `offerBlocking`（220-234 行）与 `offerDropOldest`：`BACKPRESSURE` 指标**无条件递增**，即使队列根本没满——把"尝试次数"记成了"背压事件"。
- **影响**：`audit.pipeline.backpressure` 与 `dropped` 是 README 要求必须配告警的指标；账目错则告警语义错。`dropped=0` 的"可证明不丢"在 DROP_OLDEST 策略下不成立。
- **修复方向**：`dropOldestAndOffer` 改为 CAS 循环内的原子"释放一个槽位并占用"语义，offer 失败时如实返回被丢元素（可能是新记录）；BACKPRESSURE 只在实际遇到队列满时递增。

### M3【中】哈希链未覆盖 clientIp / queryString / userAgent / tags 等归属字段

- **位置**：`AuditRecord.canonicalContent()`（138-162 行）
- **事实**：链摘要包含 id/seq/时间/主体/操作/URI/载荷/结果/耗时，但**不含 clientIp、queryString、userAgent、tags（脱敏后的 headers 就存在 tags 里）、serviceName、instanceId、principalName、sessionId、error message**。
- **影响**：对 HMAC 链（攻击者无密钥），拥有存储写权限者**直接改写 clientIp/queryString/UA 字段不会破坏校验**——来源归属（谁从哪发起）可被无痕篡改。对审计取证而言，"谁、从哪、查了什么(queryString)"恰是最需要防篡改的字段。
- **修复方向**：将全部审计语义字段纳入 canonicalContent（这是格式演进，建议随 schemaVersion=2 一次性定稿并写 ADR）。

### M4【中】`AuditMethodRegistry.find` 按裸方法名跨控制器回退匹配 → 元数据错配

- **位置**：`AuditMethodRegistry.find()`（143-162 行）
- **场景**：控制器 A 有 `@AuditLog("查询用户") getUser(Long, String)`；控制器 B 有**未标注**的 `getUser(Long)`。B 的请求查不到精确 key → 按**方法名**兜底命中 A 的元数据 → B 的审计记录带上 A 的操作名、resourceType、tags。多个控制器存在同名方法（`getById`/`list` 极常见）时是系统性错配。
- **修复方向**：回退匹配至少约束 `declaringClass` 相同；或干脆删掉回退，改为告警 + 返回 null（边界通道兜底），错配比缺语义危害更大。

### M5【中】过滤器 order=-100 与 Spring Security 默认值相同，相对顺序不确定

- **位置**：`AuditLogProperties.Boundary.order = -100`；Spring Boot 的 `springSecurityFilterChain` 注册 order 默认同样是 **-100**。
- **影响**：README/注释宣称"早于 Spring Security 的过滤器区间，使 401/403 也被记录"——同 order 值不保证先后（取决于注册顺序，不同 Boot 版本/配置组合下可翻转）。若审计过滤器排在 Security 之后，未认证请求在 Security 层被拦截时**不经过审计过滤器**（Security 的 UNAUTHORIZED 分支不继续 chain），认证失败事件漏采——恰恰是边界通道存在的首要理由。
- **修复方向**：默认 order 改为 -150（或任何严格小于 -100 的值），并在文档中说明与自定义 Security order 的协调方式。

### 低优先级（L）

| # | 问题 | 位置 | 说明 |
|---|---|---|---|
| L1 | 异常透传路径 `httpStatus=200 + outcome=FAILURE` 并存 | `AuditCaptureService.finish`（异常经 filter 抛出时容器尚未渲染错误页） | 下游按 status 统计会误判；建议异常场景 httpStatus 置 null 或补 tag |

## 四、亮点（值得保持的设计）

1. **指标归属纪律**（ADR-013）：journal 与 store 都不递增 delivered/deadletter，由 pipeline 统一计数——"指标可被审计"的意识在同类框架中罕见。
2. **`AuditLogManagementEndpoint` 的 null 安全注释**：诊断端点用 `LinkedHashMap` 而非 `Map.of`，附带了踩坑原因——代码即文档。
3. **`JacksonAuditSerializer` 的降级链**：捕获 Throwable（业务 getter 可抛 Error）、深度限制防 StackOverflow、降级占位符带类型名而非 toString。
4. **`FieldPathMatcher` 的段式匹配**：拒绝 glob→正则转换，语义上保证 `$.token` 命中任意层级——修复的是"配置了却泄漏"这类最不可接受的错误，且注释完整交代了为什么。
5. **`RegexMaskGroup` 合并预筛**：O(规则数×长度) → O(长度) 的优化有火焰图证据支撑，且语义保持证明写在了 javadoc。
6. **`AuditPipelineStartupValidator` 的防静默失效体系**：`/*` 陷阱告警、logging 存储合规告警、背压策略代价明示——把"配置看起来对但实际不工作"提前到启动期。
7. **注册表延迟填充规避循环依赖**、**不注册 `List<PrincipalResolver>` 集合 Bean**——装配脆弱点的消除都有注释留痕。
